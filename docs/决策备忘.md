# 「信标 DMR」加发射功能 —— 决策备忘

> 技术细节见 `DroidStar-逆向分析.md`。本文只讲**要决定什么**。

---

## 一、现状一句话

**技术路径已完全打通，没有未知数了。** 剩下的两个障碍都不是技术问题 ——
是 **GPL-3 许可证** 和 **AMBE+2 专利**，需要你自己权衡。

---

## 二、手上已经有什么

| 资产 | 位置 | 状态 |
|---|---|---|
| 声码器插件（Android arm64 / arm） | `vendor/droidstar-vocoder-plugin/` | ✅ 已下载归档，含 SHA256 |
| 插件 ABI 声明（可直接写代码） | `vendor/droidstar-vocoder-plugin/vocoder_plugin_abi.h` | ✅ 含精确签名、符号名、用法骨架 |
| 官方接口头文件（第二验证来源） | `vendor/droidstar-vocoder-plugin/vocoder_plugin.h` | ✅ 与 DWARF 还原结果一致 |
| 现有收听 App（可用的 APK） | `beacon-dmr-release.apk` | ✅ 606 KB，已签名，功能完整 |
| 逆向分析报告 | `DroidStar-逆向分析.md` | ✅ 9 节 |

**关键事实**：声码器接口已由**两个独立来源交叉验证**（DWARF 调试信息 + 官方头文件），
vtable 顺序、返回类型、参数语义全部确定。`encode_2450x1150()` 就是 DMR 要的
AMBE+2 编码器，20 ms → 9 字节。

**一个需要提前知道的成本**：插件依赖 `libc++_shared.so`（NDK 的 C++ 运行库，
不是 Android 系统库），必须打包进 APK。
→ **APK 会从 606 KB 增大约 1–2 MB / ABI**。这是走路线 C 的固定成本。

## 三、三条路线，代价不同

### 路线 A：不做发射，把收听做到极致

**代价**：零。**风险**：零。

通联继续用 DroidStar（它已经成熟），本 App 专注收听体验。
你现在的自动跟进、扫描、看板、录音，DroidStar 一样都没有 —— 这是差异化优势。

**适合**：不想碰 GPL 和专利，只想有个好用的收听工具。

---

### 路线 B：只做「连接器」，不做语音

**代价**：中等（几百行 Java，无 NDK）。
**风险**：低 —— 零专利问题，纯协议实现。

在 App 里新增一个 hotspot 包：UDP 连 MMDVM 主站 + `RPTL/RPTK/RPTC` 握手 + 心跳。

**验收标准很干净**：能在 BrandMeister 的 Last Heard 上看到你的 DMR ID 上线。

**副产品**：这一步做完，App 就能**直接收听你自己热点的通话**，不用再走 HOSE。

**适合**：想先要个确定的成果，把不确定性推后。

---

### 路线 C：做完整发射（含语音）

**代价**：大（NDK + C++ JNI shim + 连接器 + 半双工闸门）。
**风险**：**GPL-3 传染 + AMBE+2 专利（美国约 2028 到期）**。

技术上是通的（接口已完全确定），但：

- 插件是 **GPL-3.0-or-later**，集成并分发需评估传染性
- mbelib 的 README 有**显式专利声明**，原文直接命中我们的场景
- **DroidStar 自己在 2025-10 删掉了插件系统**，转向编译期集成 `md380_vocoder`
  （README 里同样标注专利风险）+ 串口 AMBE 硬件 —— 插件机制已无上游维护

**规避 GPL 的做法**：把声码器做成**运行时可选下载**（DroidStar 原本就是这么做的），
主程序与插件保持分离，APK 不打包插件。

**适合**：明确知道自己在做什么，且能接受自己维护。

---

## 四、我的建议

**先走路线 B，同时把路线 C 的可行性验证做掉。**

具体两步：

**第 1 步（低风险，先做）**
写一个最小的 JNI 冒烟测试：`dlopen` 插件 → 喂 160 个采样 → 看能否拿到 9 字节码字。
这一步**不碰现有 App**，独立验证声码器可用性，顺便确认两件写在 ABI 头文件里的疑问：

- **字节序**：官方注释写 `S_16_BE`（大端），但参数是 `int16_t*`（宿主序）—— 两者矛盾
- **采样率**：160 samples / 20 ms 是否确为 8 kHz

这两点不确认就动手写完整功能，字节序错了会出噪声而不是报错，很难查。

**第 2 步（拿到第 1 步结果后再定）**
- 声码器可用 → 走路线 C，先做连接器再做语音
- 声码器有问题 → 退回路线 B，或改用串口 AMBE 硬件（音质最好，绕开专利）

---

## 五、需要你拍板的两件事

1. **能不能接受 GPL-3？** 如果这个 App 只自己用，风险很小；
   如果要分发，建议走「运行时下载插件」的分离架构。
2. **发射要用来做什么？** 如果只是自己测试/实验，和「公开发布给别人用」
   是完全不同的合规要求。这一条会直接改变技术选型。

---

## 六、如果继续，下一步的动作

```
1. 写 JNI 冒烟测试（新建 app-android/app/src/main/cpp/，不动现有 build.gradle）
2. 在手机上验证：dlopen 成功 → encode_2450x1150 产出 9 字节 → 字节序确认
3. 按结果决定是否继续做连接器
```

**第 1、2 步不需要任何外部依赖，也不需要网络，纯粹是本地验证。**
