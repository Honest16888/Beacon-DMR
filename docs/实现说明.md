## 二、三条链路的分工

发射没有复用收听链路 —— 它们是两套完全独立的协议：

| 链路 | 协议 | 端口 | 用途 |
|------|------|------|------|
| 收听 | HOSE over WebSocket | 443 (wss) | 实时音频、活动流，**原有功能不动** |
| 发射 | MMDVM / Homebrew over UDP | 62031 | 登录主站、发 DMRD 包 |
| 声码器 | 本地 .so（dlopen） | — | PCM ↔ AMBE+2 编解码 |

**半双工闸门**：按下 PTT 时自动静音 HOSE 播放（`setPlay(false)`），松开后恢复，
避免听见自己绕网络回来的声音。

## 三、登录握手（逐字节，照搬 DroidStar 实现）

```
客户端 → RPTL  + id(4, 大端)                                   8 字节
主站  → RPTACK + id(4) + salt(4)                              10 字节
客户端 → RPTK  + id(4) + SHA256(salt_原始4字节 ‖ 密码UTF8)     40 字节
主站  → RPTACK + id(4)                                        10 字节
客户端 → RPTC  + id(4) + 配置串(294)                          302 字节
主站  → RPTACK + id(4)                                        10 字节   → 可收发

保活：RPTPING + id(4)  11 字节，每 5 秒；主站回 MSTPONG + id(4)
断开：RPTCL + id(4)     9 字节
```

两个容易写错的地方：

1. **salt 是「4 字节位模式」**，直接按原始字节顺序拼在密码**前面**做 SHA-256，
   既不做字节序转换，也不当整数解析。
2. **RPTACK 出现三次，含义完全不同**，报文本身没有任何区分标志，
   只能靠本地状态机（CONNECTING → AUTH → CONF → CONNECTED）区分。

## 四、DMRD 包与 AMBE 交织（最容易错的部分）

55 字节：

```
[0..3]   "DMRD"
[4]      seqNo
[5..7]   srcId   (24 位大端)
[8..10]  dstId   (24 位大端)
[11..14] repeaterId (32 位大端)
[15]     标志：bit7 时隙 | bit6 FLCO | bit5 数据/同步 | bit4 语音同步 | bit3..0 帧内序号
[16..19] streamId
[20..52] 33 字节 DMR 载荷
[53]     BER = 0
[54]     RSSI = 0
```

**27 字节 AMBE 在 33 字节载荷里是位级交织的，不是简单拼接**：

```
payload[0..12]  = ambe[0..12]
payload[13]     = (原值 & 0x0F) | (ambe[13] & 0xF0)   ← ambe[13] 的高 4 位
payload[14..18] = 同步码 / 嵌入信令
payload[19]     = (原值 & 0xF0) | (ambe[13] & 0x0F)   ← ambe[13] 的低 4 位
payload[20..32] = ambe[14..26]
```

也就是说 `ambe[13]` 被拆成两半，分别塞进 `payload[13]` 和 `payload[19]`，
中间 5 个字节让给同步码和嵌入 LC。

**发射时序**：

```
按下 PTT
  ├─ 立即发 1 个语音 LC 头帧（DT_VOICE_LC_HEADER，seqNo=0）
  └─ 采集线程：每读满 160 个 8 kHz 样本（20 ms）编出 9 字节 AMBE，
               攒够 3 帧（27 字节 / 60 ms）打一个 DMRD 包
松开 PTT
  └─ 发 1 个终止帧（DT_TERMINATOR_WITH_LC）
```

DroidStar 用 19 ms 定时器 + 非阻塞读（"问得比音频时钟快"来避免欠载）；
本实现改用**阻塞式 `AudioRecord.read`**，直接跟音频设备时钟对齐，无漂移。

## 六、怎么用

1. 装 APK（`beacon-dmr-debug.apk` 或已签名的 release 版）。
2. 切到「📡 发射」页 —— 会自动尝试加载声码器。
3. 点 **加载声码器**，看自检报告。**这一步必须先通过**。
4. 点 **申请麦克风权限**。
5. 填主站地址（如 `brandmeister.network`）、DMR ID、**热点安全密码**。
   > 密码是 BrandMeister SelfCare 里的「热点安全密码」，**不是账号密码**。
   > 见 help.brandmeister.network/dashboard/hotspot-security/
6. 填目标话组（默认 91 世界组）、时隙、色码，点 **连接主站**。
   若主站回 `MSTNAK`，**不要反复点** —— 按钮会变成「正在登录…」，
   App 会自己按 10 / 20 / 40 / 60 秒逐档等待重试（累计约两分钟）。
7. 状态显示「已连接」后，**按住 PTT 说话，松开结束**。

**建议第一次先用 Parrot 回声测试**：呼叫类型选「私呼」、目标填 `460997`，
按住 PTT 说一句再松开，能听到自己声音回放就说明整条发射链路通了。

两个诊断按钮：

- **FEC 自检** —— 不需要声码器，用假 AMBE 走完整条 FEC 链并 dump 三帧十六进制，
  用来单独验证帧组装是否正确。
- **复制报告** —— 把最近一次自检报告一键复制到剪贴板。报告有六七十行，
  手抄容易漏，点这个按钮再粘贴回来即可。

### 怎么确认「发射到底通没通」

**最直接的办法：Parrot 回声测试。**

把「呼叫类型」改成 **私呼**，目标填 `460997`
（BrandMeister 的 Parrot 服务，MCC 460 + 997；换其它主站就是 `<MCC>997`）。
按住 PTT 说一句话再松开，几秒后会把你的声音原样回放给你。
**听到回放 = 发射链路完全打通**，不需要任何其他人在线。

**第二个办法：看 App 自己的实时活动看板。**
发完切到收听页看 Last Heard，如果自己出现在里面，说明上行已经到网。

### 卡在「正在登录」怎么排查

App 现在会**把握手全过程打进日志**，包括每个包的十六进制和收包计数。
点「**复制日志**」把整段发回即可定位。日志会给出这几条关键信息：

| 日志内容 | 含义 |
|---|---|
| `域名 ... 解析到 N 个地址` | DNS 通了。**N 个地址都会依次尝试**，不再是只试第一个 |
| `本机 UDP 端口 xxxxx` | 本地套接字建好了 |
| `→ 8 字节 [RPTL....] ...` | RPTL 发出去了 |
| `← 10 字节 [RPTACK..] ...` | 主站应答了，握手在推进 |
| `收到主站报文 0 个` | **一个包都没回来** → 网络层问题，不是密码问题 |

24 秒没走完握手会自动报错，并给出可执行的建议。

**判定树**：

1. **日志里有 `←` 开头的行** → 包能通，问题在协议或凭据。看卡在哪一步：
   停在 `AUTH` 说明密码不对（或 ID 未登记热点）；停在 `CONF` 说明呼号/配置串被拒。
2. **日志里一个 `←` 都没有** → 包根本没到主站。依次查：
   - **换网络再试**（Wi-Fi ↔ 移动数据）。有些网络会阻断出向 UDP 62031。
   - **到 BrandMeister Dashboard → Device Logs 看有没有登录记录**。
     一条都没有 = 包没到主站，跟密码无关。
   - 确认地址是 `4602.master.brandmeister.network`、端口 `62031`。
3. **官方排障页明确要求**：呼号与 Radio ID 必须与 RadioID 注册信息一致；
   热点安全密码必须已在 SelfCare 里为该 ID 设置。
   见 help.brandmeister.network/hotspots/common-connection-issues/

### 主站返回 MSTNAK、要连很多次才连上（第三轮修复）

真机第二轮反馈：**主站返回 `MSTNAK`，反复点「连接主站」若干次后能连上；
断开之后又要多次点击才能连上。**

**这个现象本身就是诊断结论。** 如果密码错了，就**永远不会**成功；
既然反复点最终能连上，说明**凭据是对的，主站只是暂时性拒绝**。

原因查证如下 —— **一个 Radio ID 同时只能有一个会话**。BrandMeister 官方 FAQ 原文：

> You will set the Hotspot Security password for the Radio ID that is being used
> and then may use that same password on multiple devices if using the same Radio ID
> for each one (**plus the alias id if using multiple hotspots**).

也就是说同一个 ID 想同时挂两个热点，必须另配 **alias id**。旧会话被顶掉后有约
**15 秒**的 hand-off 计时器（官方 wiki 的 UK 页面写着 `Hand-Off Timer: 15 seconds`），
这期间同 ID 重新登录会被直接拒绝 —— 表现就是 `MSTNAK`。

**原来的代码把 `MSTNAK` 当成致命错误**（`setState(ERROR)` + 关套接字），
所以只能靠用户反复手点，点中旧会话刚好过期的那个瞬间才能连上。

**修法**（全在 `MmdvmSession.java`）：

| 改动 | 说明 |
|---|---|
| `MSTNAK` 不再致命 | 不报错、不关套接字，进入自动重试链 |
| **等待逐次加长** | `NAK_WAITS_MS = {10000, 20000, 40000, 60000}`（累计约两分钟）。**注意：官方 wiki 写的 Hand-Off Timer 是 15 秒，但实测不像只有 15 秒** —— 用户「反复点十几次才连上」意味着窗口在 30~60 秒量级，所以档位按 60 秒级覆盖 |
| **最多重试 4 次** | `MAX_NAK = 5`，第 5 次才放弃并给出「先关掉其它用同一 ID 的设备」的建议 |
| 断开后重连不再猛冲 | `POST_DISCONNECT_WAIT_MS = 2000`，给 RPTCL 生效的机会；真没生效由 MSTNAK 重试链兜住 |
| **只在真连上过时才等** | 新增 `hadSession` 标志。从头到尾没连上的失败尝试，再点连接不需要等任何窗口 |
| **握手途中不再插 RPTL** | 状态进入 `AUTH` / `CONF` 后绝不重发 RPTL —— 重复发会让主站看到同 ID 的第二次登录，直接回 `MSTNAK`，这正是「要点很多次」的成因之一 |
| 停滞检测 | `AUTH` / `CONF` 停超过 `STALL_MS = 8000` 才从头重来（UDP 丢包时不能干等） |
| **断开时也发 RPTCL** | 原来只在 `CONNECTED` / `CONF` 发；现在 `AUTH` 之后都发 —— 主站在 `AUTH` 时可能已经建了会话，少发一个登出就要靠它的计时器回收 |
| **密码首尾空格自动去掉** | 官方 FAQ 专门警告：「you may have accidentally copied a space at the beginning or end of the password when you copied and pasted it」。现在会自动 `trim()` 并在日志里提示 |
| **`MSTCL` 自动重连** | 主站主动关闭连接（多是被别的设备用同一 ID 顶掉，或主站重启）不再直接报错停下。上游 DroidStar 在这里是 `request_reconnect(10000)`，我们照做：10 秒后自动重连，上限 3 次，防止凭据真不对时无限循环 |
| 自动重连可被用户取消 | 用「会话代数」`sessionGen` 标记：用户按了「断开」，排队的自动重连就作废，不会断了又自己连回去 |

界面上也做了配合：握手三个阶段按钮显示「**正在登录…**」并禁用，
重复点击会提示「正在登录中，请稍候（被暂时拒绝会自动重试）」，
避免用户因为看着像卡住而反复点、反而把成功的路堵住。

**给使用者的结论**：`MSTNAK` 现在**不用管它**，App 会自己按 10 / 20 / 40 / 60 秒重试。
如果三次都失败，先确认没有**其它设备**（热点盒子、另一台手机）正在用同一个 DMR ID。

### 卡在「主站暂时拒绝（ID 可能已在线）」不动（第四轮修复）

真机第三轮反馈：装上上一版后，界面**一直显示「主站暂时拒绝（ID 可能已在线）」不再变化**，
用户也确认**没有别的设备在用同一个 DMR ID**。

「一直不动」本身就是线索：按上一版的逻辑，最多 38 秒就该走到「连续 3 次拒绝」并报错。
**卡住不动说明重试线程已经死了。** 根因：

```java
while (running && state != State.CONNECTED && state != State.ERROR) { … }
```

握手线程在进入 `CONNECTED` 的那一刻就退出了。此后若主站又发来 `MSTNAK`
（把状态推回 `CONNECTING`、并显示「N 秒后自动重试」），**已经没有任何线程负责重试**
—— 界面就永远停在那一行。

顺带查了 MMDVMHost 的参考实现（`DMRDirectNetwork.cpp`），发现我上一版的另一处也错了：

```cpp
} else if (memcmp(buffer, "MSTNAK", 6) == 0) {
    if (m_status == RUNNING) { m_status = WAITING_LOGIN; … }   // 已登录被拒 → 重发 RPTL
    else { close(false); open(); return; }                     // 未登录被拒 → 整个网络重连
}
// 重试定时器到期时（分状态！）：
case WAITING_LOGIN:         writeLogin();         break;  // RPTL
case WAITING_AUTHORISATION: writeAuthorisation(); break;  // RPTK —— 不是 RPTL
case WAITING_CONFIG:        writeConfig();        break;  // RPTC —— 不是 RPTL
```

我上一版写的是「握手停滞就退回重发 RPTL」，而**重发 RPTL 等于告诉主站
「同 ID 又登录了一次」**，正好自己招来 `MSTNAK`。

| 改动 | 说明 |
|---|---|
| **新增 `ensureHandshakeThread()`** | 凡是把状态推回 `CONNECTING` 的地方都补一次握手线程。加 `hsLock` 同步，避免 rx / ping 两个线程同时补出两个握手线程（两个都发 RPTL 同样是重复登录） |
| **ping 线程兼作看护** | 每 5 秒检查一次：没连上却没有握手线程在跑就补一个。因为握手线程退出与「被推回 CONNECTING」可能撞在同一瞬间（`isAlive()` 还是 true，ensure 就没补上），单靠 `ensure` 有个小窗口兜不住 |
| **停滞时按状态重发** | `AUTH` → 重发 `RPTK`；`CONF` → 重发 `RPTC`。**绝不退回 RPTL**。为此把发出去的 `lastRptk` / `lastRptc` 留一份 |
| **未登录被拒 → 换新套接字** | 对齐 MMDVMHost 的 `close(); open();`。新源端口常能让主站把这次登录当成全新设备，绕开「旧会话没释放」。`restartSocket()` 先切字段再关旧套接字，`rxLoop` 发现套接字被换就接着读新的 |
| **倒计时每秒刷新** | 等待期间把剩余秒数刷到状态栏与日志的**同一行**（`txLogProgress` 原地改写，不刷屏）。数字在动，就不会再被误判成卡死 |
| **拒绝时按阶段给结论** | `MSTNAK` 时记下当时处在哪一步：`CONNECTING` → ID 被占；`AUTH` → 密码/未登记热点；`CONF` → 呼号不符；`CONNECTED` → 被同 ID 顶掉。四种情况给完全不同的排查建议 |
| 重试档位放宽 | `{10s, 20s, 40s, 60s}`，`MAX_NAK = 5`（前 4 次都自动重试），累计约两分钟，覆盖 60 秒级的会话回收 |
| **被拒时主动发 RPTCL** | 占着会话的很可能就是本 App 上一次没断干净的连接（进程被杀时来不及登出）。第一次 MSTNAK 时先替主站登出一次再重登；主站若不认这个未认证的 RPTCL，也只是忽略 |
| 倒计时里带阶段 | 显示「停在 CONNECTING / AUTH / CONF」，截个图就能定位是「ID 被占」还是「凭据不对」 |

失败信息里也加了**最实用的一招**：到 Dashboard → Hotspots 看有没有这个 ID 的热点显示在线；
以及**把主站地址换成另一台**（旧会话是挂在具体主站上的，换一台常常立刻就能进）。

### 密码通过了、却卡在 RPTC 被拒 —— 真凶是「源端口一直在变」（第五轮修复）

真机第四轮反馈给了一段完整日志，关键三行：

```
→ RPTK（salt + 密码的 SHA-256）   ← RPTACK + id      ← 密码通过了
→ RPTC（294 字节配置串，BH6RGQ）  ← MSTNAK           ← 被拒在配置这一步
```

**先把「配置串写错了」这个方向彻底排除。** 我把上游两份权威实现取回来逐字段对照：

| 参考实现 | 结果 |
|---|---|
| `nostar/MMDVMHost` → `DMRDirectNetwork.cpp` → `writeConfig()` | 格式串 `"%-8.8s%09u%09u%02u%02u%8.8s%9.9s%03d%-20.20s%-19.19s%c%-124.124s%-40.40s%-40.40s"`，字段宽合计 294，总包 302 |
| `nostar/DroidStar` → `dmr.cpp` → `DMR_AUTH` 分支 | 同一格式串，`1, 1, '4'` 三个常量也一模一样 |

我们的 `buildRptc()` 与这两份**逐字节一致**。所以配置串本身没问题 ——
问题在「主站怎么看这台热点」。

**去查这个 ID 在主站侧的真实记录**（BrandMeister 有公开设备 API）：

```bash
curl https://api.brandmeister.network/v2/device/4614187
```

```json
{"id":4614187,"callsign":"BH6RGQ","linkname":"MMDVM Host",
 "hardware":"MMDVM_MMDVM_HS_Hat","firmware":"20181107_Pi-Star",
 "tx":"438.8000","rx":"438.8000","colorcode":1,
 "status":4,"statusText":"DMO","lastKnownMaster":4602,
 "last_seen":"2026-09-29 17:26:18","permissions":[]}
```

这条记录回答了四件事：

1. **ID 与呼号匹配、主站认识这个 ID** → 不是注册问题。
   （`hardware` 字段就是 RPTC 第 14 字段的原字符串，证明主站确实解析并保存了 RPTC。）
2. `statusText: "DMO"` → 主站接受过 `slots = '4'`，我们那个 `'4'` 是对的。
3. `hardware` 仍是 `MMDVM_MMDVM_HS_Hat`、`last_seen` 停在 **9/29 17:26**
   → **本 App 从来没有成功完成过一次 RPTC**（否则这里早该变成我们的软件名、日期也该是今天）。
4. 这个 ID 上次用的是 **Pi-Star 热点**（`firmware: 20181107_Pi-Star`）。

**真凶找到了：本 App 从来没有固定的源端口。**

```java
DatagramSocket s = new DatagramSocket();   // 每次连接 → 随机临时端口
fresh = new DatagramSocket();              // 每次重试 → 又换一个端口
```

主站是**按「IP + 源端口」来认一台热点**的；真实热点（Pi-Star / MMDVMHost）
在 `MMDVM.ini` 里写死 `Local=62031`，一辈子只用一个端口。而我们的 App 每轮换一个端口，
主站眼里就是**同一个 Radio ID 下不断冒出新热点** —— 于是按
「一个 Radio ID 只允许一台热点在线」的规则，在 RPTC 阶段回 `MSTNAK`。

更要命的是**它自我放大**：越重试，留在主站会话表里的幽灵热点越多，
于是越重试越连不上。日志里那句 `已换新 UDP 套接字，本地端口 39197`
就是每轮自招一次拒绝。这也解释了为什么之前「反复点十几次偶尔能连上」——
偶尔点中的那次，恰好前面几个幽灵会话都过期了。

| 改动 | 说明 |
|---|---|
| **固定本机 UDP 端口** | 新增 `openSocket()`：优先绑 `62031`，被占则顺延试 `62031..62050`，全被占才退回临时端口，**且该临时端口只在本次运行内取一次**。整个进程生命周期端口不变 —— 对齐真实热点的 `Local=62031` |
| **断开重连也复用同一端口** | `disconnect()` 只置空 `socket`，`localPort` 保留；下次连接仍绑同一个端口。这样重连在主站眼里是**同一台热点重新登录（接管）**，而不是「又来一台新热点」 |
| **收到 `MSTNAK` 绝不换端口** | 删掉了「未登录被拒 → `needSocketRestart = true`」。链路既然能收到 NAK 就是通的，换端口有百害而无一利 |
| **`restartSocket()` 只用于「完全没有回音」** | 触发条件改成「连发 ≥4 个 RPTL 且一个回包都没收到」（本地套接字 / NAT 映射坏了），并且**端口保持不变** |
| **`restartSocket()` 改为先关后开** | 原顺序是「先开新套接字、再关旧的」—— 同一个 UDP 端口不能重复 `bind`，不先关就绑不上，`openSocket()` 会误判端口被占而换端口，正好破坏要保住的东西。现在：置空引用 → 关旧 → 绑新；`rxLoop` 容忍瞬间的空引用（不 `break`，`sleepQuiet(50)` 后重看） |
| **删掉「被拒时主动发 RPTCL」** | 上游 MMDVMHost 只在 `m_status == RUNNING`（真正登录成功后）才发 RPTCL。从一个**从未登录成功**的套接字发 RPTCL 毫无意义，只是噪声 |
| **RPTC 第 14 字段不再留空** | `packageId` 从 `""` 改成 `"BeaconDMR_Android"`。该字段对应主站记录里的 `hardware`，真实热点这一栏总有值 |
| 重试档位与上限 | `NAK_WAITS_MS = {10000, 20000, 30000, 45000, 60000}`，`MAX_NAK = 6`（前 5 次自动重试，累计约 165 秒） |
| 失败信息指向一手证据 | 明确让用户去 **Dashboard → Device Logs**（主站直接写明拒绝原因）、**Dashboard → Hotspots**（看该 ID 是否显示在线）、**换一台主站**（会话挂在具体主站上） |
| 日志带端口 | 每次 MSTNAK 都打印「本机端口 N」，重试日志写明「用同一个端口重试」，一眼能看出端口没变 |

**顺带得到一个自助核查工具**：任何时候都可以用

```bash
curl https://api.brandmeister.network/v2/device/<你的DMR_ID>
```

看 `hardware` 和 `last_seen` —— 如果 `hardware` 不是 `BeaconDMR_Android`，
就说明我们的 RPTC 还没被接受过；如果 `last_seen` 是很久以前，
说明最近这些尝试一次都没成功。

### 第二轮（卡在「正在登录」）为排查做的改动

- **去掉了「按来源 IP 丢弃报文」的过滤**。上游 DroidStar / MMDVMHost 都不做这个；
  主站有多条 A 记录时，应答可能来自另一个地址，过滤会把登录应答直接丢掉 ——
  表现正是「一直卡在正在登录」。现在只记一笔警告，照常处理。
- **DNS 解析全部地址**（`getAllByName`），连试两轮无回音就自动换下一个地址。
- **RPTL 每 3 秒重发**，最多 8 次（UDP 无重传，主站偶尔会吞第一个包）。
- **24 秒握手看护**，超时给出上面的判定建议；并把 `running` 放掉，
  免得用户不按「断开」就再也连不上。
- 日志新增 **收发包计数** 与 **握手报文十六进制**。

## 八、声码器自检（第二版，判据已重写）

第一版自检在真机上把「通过」误报成了「失败」。原因**不在插件，在自检自己**：

| 第一版的缺陷 | 为什么是错的 | 第二版怎么改 |
|---|---|---|
| 只比**单帧** 160 采样，lag 只扫 ±96 | `imbe_vocoder.h` 的 `PITCH_EST_FRAME = 301` —— 编码器基音估计用了 301 点窗，编解码链路有几百采样延迟，单帧比较必然错位 | 改成 **120 帧（2.4 秒）连续序列**，lag 扫 ±600 |
| 编解码**共用同一个实例** | 上游 `encode_ambe()` 末尾调 `mbe_moveMbeParms(cur_mp, prev_mp)`，而解码路径 `mbe_processAmbe3600x2450Framef()` 也写这两个参数 → 状态互相污染 | 编、解码**各用一个实例**（生产代码也改了，见下） |
| 只测**纯正弦**，幅度仅满量程 1/4 | AMBE 基音范围约 50~400 Hz，1 kHz 正弦根本不在范围内；孤立的单频也不具备语音谐波结构，会被判成「无声」。声码器**正常工作时**也会这样 | 换成**类语音**信号：基频 120 Hz + 24 次谐波 + 双共振峰 + 音节起伏，峰值 24000 |
| 主判据是**波形相关性** | AMBE 会重建相位，波形对不上是正常的 | 主判据改为**包络相关性**；另加一条完全不依赖相关性的硬判据 |

**第二版自检的九项**

| 项 | 问的问题 | 判据 |
|---|---|---|
| Q1 | dlopen 成功吗 | — |
| Q2 | 四个符号能解析吗、`create()` 有效吗 | — |
| Q3 | 编码是否只写 9 字节 | 第 9 字节之后 23 字节未被改动 |
| Q4 | 测试信号是什么 | 打印长度与峰值 |
| Q5 | **编码器真的读输入吗** | 静音 / 类语音 / 噪声三种输入的码字**必须不同** |
| Q6 | **解码器有输出吗** | 静音码字解码 RMS≈0，有声码字 RMS 显著大于 0 |
| Q7 | 包络跟随吗、延迟多少 | 包络相关 > 0.5；另附波形域延迟扫描 + 大端交叉验证 |
| Q8 | 音调保住了吗 | Goertzel 测出的主频应落在 100~260 Hz |
| Q9 | 编码确定吗 | 同输入同初态跑两遍，比特差异应为 0 |

Q5 和 Q6 是**最硬的两条**：它们不依赖任何相关性假设。
Q5 失败 = ABI/调用层面的问题；Q6 失败 = 解码侧或码字格式问题。

**字节序问题已有定论，不必再猜**
上游 `mbevocoder.h` 里输出缓冲的注释明写：

```cpp
short m_audio_out_buf[2*48000];  //!< final result - 1s of L+R S16LE samples
```

而 `decode_2450x1150()` 是裸 `memcpy(pcm, p, samples * sizeof(int16_t))`。
所以 **PCM 是宿主序（ARM 上即小端）**，不需要 byte-swap。
ABI 头里那句 `S_16_BE` 是 DVSI AMBE-3000 硬件串口接口的遗留描述，不适用于插件。

### 顺带修掉的一个真实缺陷

上一版**生产代码**（不是自检）里，编码和解码共用一个声码器实例。
上游 `MBEVocoder` 的 `m_cur_mp` / `m_prev_mp` 同时被两边读写，
后果是「刚收完立刻发」时，编码器会从对端的参数状态起步，头几帧失真。
现已改为 **`g_enc` / `g_dec` 双实例**，互不干扰，代价约 190 KB 内存。

### 真机第一轮反馈修掉的 bug

用户反馈「自检结果正常，但声码器显示未加载」。根因：

```java
// 错：nativeProbe 用的是**独立的临时实例**，不会填充生产用的 g_enc / g_dec
vocoderReport = Vocoder.nativeProbe(path);
vocoderReady  = Vocoder.nativeIsReady();   // 永远 false
```

`【注意】` 行说明失败原因。

## 十一、ESSID / 别名 ID：MSTNAK 的真凶（第六轮修复，2026-10-12）

### 11.1 结论先说

**「主站暂时拒绝」不是我们代码写错了，是身份冲突。**

主站按 Radio ID 认设备，**一个 DMR ID 只允许一台热点在线**。
而这个 ID 上早就挂着一台 Pi-Star —— 主站的设备记录直接写着：

```json
// https://api.brandmeister.network/v2/device/4614187
{"id":4614187,"callsign":"BH6RGQ","hardware":"MMDVM_MMDVM_HS_Hat",
 "firmware":"20181107_Pi-Star","status":4,"statusText":"DMO",
 "lastKnownMaster":4602,"last_seen":"2026-10-07 07:19:51"}
```

三条关键信息：

- `hardware` 一直是 `MMDVM_MMDVM_HS_Hat`、`firmware` 一直是 `20181107_Pi-Star`
  → **我们的 App 从未成功完成过 RPTC**（成功了这里就会变成 `BeaconDMR_Android`）
- `last_seen` 还在往前滚（9/29 → 10/7）→ 那台热点是活的
- 所以：**它占着会话，我们再用同一个裸 ID 登录，必然被 MSTNAK，等多久都没用**

### 11.2 上游源码对照：我们的握手实现是对的

把 `nostar/MMDVMHost` 的 `DMRDirectNetwork.cpp` 取回逐字节对照，结论是**没有缺陷**：

| 项目 | 上游 | 我们 |
|------|------|------|
| RPTL | `"RPTL" + id(4)`，8 字节 | 同 |
| salt 偏移 | `memcpy(m_salt, m_buffer + 6U, 4)` → `[6..9]` | `{buf[6],buf[7],buf[8],buf[9]}` |
| RPTK | `"RPTK" + id(4) + SHA256(salt ‖ password)`，40 字节 | 同 |
| RPTC | 302 字节，格式串 `%-8.8s%09u%09u%02u%02u%8.8s%9.9s%03d%-20.20s%-19.19s%c%-124.124s%-40.40s%-40.40s` | 同 |
| `slots` | DMO 时 `'4'` | `'4'` |
| 停滞重发 | `clock()` 里按 `m_status` **分状态**重发，不退回 RPTL | 同 |
| MSTNAK | 未登录 → `close(false); open();`；已登录 → 退回 `WAITING_LOGIN` | 同 |

**所以问题不在协议实现，在「我们是谁」。**

### 11.3 解法：ESSID / 别名 ID

BrandMeister 官方文档（`pi-star-mmdvm/README.md`）原文：

> **BrandMeister Network ESSID**（也叫 DMR ESSID）：给热点选一个别名。
> **第一个热点可以用 01 或者留空（none）。如果你打算用多个热点，
> 就应该选 01~99 —— 每个热点必须有唯一的 ID，ESSID 就是为此而设。**

配了别名之后，登录 ID 变成 **9 位**：

```
DMR ID 4614187  +  ESSID 01   →   登录 ID 461418701
```

在主站眼里这就是**一台独立的热点**，可以和原来那台 Pi-Star 同时在线、互不打扰。
（实测 `461418701` / `461418702` 在 `api.brandmeister.network/v2/device/` 下都是 404，
说明这些别名还没被占用。）

**ESSID 不需要在 SelfCare 里额外登记** —— Pi-Star 里它就是一个下拉框，
选完就生效，主站自动认。

### 11.4 代码改动（参数链贯通）

关键点：**「登录 ID」和「本机 Radio ID」是两回事**，必须分开。

| 用途 | 用哪个 ID | 为什么 |
|------|-----------|--------|
| RPTL / RPTK / RPTC / RPTPING / RPTCL | **loginId**（含 ESSID） | 主站据此找设备记录、判唯一性 |
| DMRD 头 `[5..7]` srcId | **dmrId**（裸 7 位） | 呼号归属，是「谁在说话」 |
| DMRD 头 `[11..14]` repeaterId | **loginId**（含 ESSID） | 标识「经哪台热点中继」，通联记录归到正确热点 |

Java 侧：

```java
// MmdvmSession
private volatile int essid = 0;
private volatile int loginId = 0;

public void configure(String host, int port, int dmrId, int essid, String password) {
    ...
    int ess = essid;
    if (ess < 0 || ess > 99) { log("ESSID 只支持 01~99，收到 " + essid + "…"); ess = 0; }
    this.essid = ess;
    this.loginId = ess > 0 ? dmrId * 100 + ess : dmrId;   // dmrId 最大 16777215，不会溢出
    ...
}
```

五处 `putBE32(..., dmrId)` 全部改成 `loginId`（RPTL / RPTCL / RPTK / RPTPING / RPTC）。
`buildRptc()` 里的呼号仍按裸 `dmrId` 兜底 —— 身份是人的，不是热点的。

native 侧（`dmrtx_jni.cpp`）新增 `repeaterId` 字段与 `nativeSetRepeaterId`：

```cpp
f[11U] = g_tx.repeaterId >> 24;   // 之前是 g_tx.srcId
f[12U] = g_tx.repeaterId >> 16;
f[13U] = g_tx.repeaterId >> 8;
f[14U] = g_tx.repeaterId >> 0;
```

`nativeSetParams` 里默认 `repeaterId = srcId`（不配别名时两者相同），
配了别名时 Java 侧再调 `nativeSetRepeaterId(loginId)` 覆盖。
`nativeSelfTest` 里也补了 `g_tx.repeaterId = 4601234`，自检输出才完整。

参数链：
`dmr-listener.html` → `Android.dmrConnect(host,port,id,ess,pwd,call,loc,desc)`
→ `DmrEngine.connect(...)` → `MmdvmSession.configure(...)`。
`dmrStatus()` 也新增返回 `loginId` / `essid`，界面据此显示「实际用哪个 ID 登录」。

旧文案是 `主站暂时拒绝（ID 可能已在线），N 秒后自动重试…` —— 含糊、且没告诉用户怎么办。

## 十二、通联：MMDVM 接收链路 + 「对讲」页（第七轮，2026-10-16）

### 12.1 为什么从「发射」改叫「通联」

参考对象是一台 **ESP32 硬件对讲机**（AI Passport 上的「BrandMeister 随身对讲」）：
连 Wi-Fi 直连 BrandMeister，上下键选信道、**按住 OK 说话、松开收听**，支持组呼 / 个呼。
它和本 App 之前的差别只有一条，但很关键：

| | 之前 | 参考设备 | 本轮之后 |
|---|---|---|---|
| 发 | MMDVM | MMDVM | MMDVM |
| 收 | **Hoseline（另一条链路、只转播组呼）** | **同一条 MMDVM 链路** | **同一条 MMDVM 链路** |

Hoseline 是 BrandMeister 的公共转播流：延迟一两秒、**只转播组呼**、
而且是「大家共用的一个流」。要真做对讲机，接收必须走回 MMDVM 本身 ——
主站会把你这台热点订阅到的话组流量以 DMRD 包推给你，解出来就是音频。

所以这一轮补的是**接收解调链路**，页签也从「发射」改名为「对讲」。

### 12.2 接收链路：DMRD 载荷 → 解交织 → AMBE → PCM

新增 `DmrRx.java`，是 `dmrtx_jni.cpp` 里 `interleave_ambe()` 的**精确逆运算**。

一个 DMRD 语音包 55 字节，其中 `[20..52]` 的 33 字节载荷**不是**裸 AMBE ——
它是空中突发的载荷，27 字节 AMBE 被「织」进 33 字节里，腾出 48 bit 放同步码与嵌入信令。

**位缝分配（这是能对上的关键，逐位核对过）：**

```
interleave_ambe()   写：p[0..12] 全字节 · p[13] 高半字节 · p[20..32] 全字节 · p[19] 低半字节
addDMRAudioSync()   写：p[13..19]，被 SYNC_MASK = {0F,FF,FF,FF,FF,FF,F0} 掩过
get_emb_data()      写：p[13] 低半字节 · p[14] 高半字节 · p[18] 低半字节 · p[19] 高半字节
```

`SYNC_MASK[0]=0x0F` 只吃 `p[13]` 低半字节、`SYNC_MASK[6]=0xF0` 只吃 `p[19]` 高半字节，
而 AMBE 占的正是 `p[13]` **高**半字节与 `p[19]` **低**半字节 —— **互不重叠**。
所以解交织能把 27 字节一字不差取回来：

```java
System.arraycopy(payload, off, out, 0, 13);
out[13] = (byte) ((payload[off + 13] & 0xF0) | (payload[off + 19] & 0x0F));
System.arraycopy(payload, off + 20, out, 14, 13);
```

然后 3 帧 × 9 字节分别喂 `Vocoder.nativeDecode`（**这个接口一直都在，
只是从来没人调用过**），得到 480 个采样 = 60 ms @ 8 kHz。

> **踩坑**：`Vocoder.nativeDecode(codec, pcm)` **没有偏移量参数**，
> 一次只能吃「整整 9 字节」的数组，所以每帧要先拷进一份 9 字节临时缓冲。

### 12.3 抖动缓冲与播放（`DmrAudio.java`）

主站每 60 ms 推一个包，网络抖动会让包时快时慢，直接写 `AudioTrack` 就会一顿一顿。
中间垫一层队列：

```
DmrRx.decode() ──► feed() ──► [ArrayBlockingQueue] ──► 写线程 ──► AudioTrack
                                      ↑
                            先攒够 jitterFrames 再开声
```

- **预填充是抖动缓冲的全部意义**：第一个包到达时先不出声，攒到 `jitterMs`
  那么厚再开始播。攒得越厚越抗抖动，代价是延迟越大 ——
  参考设备上那个「网络不稳时加长接收缓冲」调的就是这个值。默认 **240 ms**，可调 0~600。
- **一句播完就复位**：360 ms 没有新包视为说完，复位后下一句重新预填充，
  免得上一句余音和下一句首字粘在一起。
- 增益在这里做（不是解码时），因为音量要能实时改；允许 >1 让弱信号听得见，代价是可能削顶。
- 队列满时**丢最旧的**，绝不阻塞接收线程。

### 12.4 通话组怎么来 —— BrandMeister **不需要** RPTO

查 `MMDVMHost/MMDVM.ini` 原文：

```ini
[DMR Network]
# Type may be either 'Direct' or 'Gateway'. When Direct you must provide the Master's
# address as well as the Password, and for DMR+, Options also.
Type=Gateway
```

**`Options`（也就是 `RPTO` 报文）只在 DMR+ / IPSC2 上需要**，BrandMeister 走
`Type=Direct` 时不发。所以本机不发 RPTO —— 和 Pi-Star 的脾气一样：

- 在 **SelfCare 里设成静态话组**的，主站一直推；
- **按住 PTT 在某话组上说过话**，该话组被**动态激活约十分钟**。

这一点已写进对讲页的「接收」卡片说明里，免得用户以为「选了信道就该马上有声音」。

### 12.6 半双工闸门（扩展）

原来的闸门只在发射时掐 HOSE。现在接收（走 MMDVM）也要掐 ——
否则同一句话会从 MMDVM 与 Hoseline 各听一遍（差一两秒，像回声）。
合并成一个函数，`tx` 与 `rx` 事件都调它：

```js
function hdGate(){
  const busy=TX.txing||Q.rxing;
  if(busy){ if(state.audioOn){ Q.hd=true; setPlay(false); } }
  else if(Q.hd){ Q.hd=false; if(!state.audioOn)setPlay(true); }
}
```

原生侧另有一道保险：`DmrEngine.onTxStart()` 里 `audio.flush()`，
发射瞬间把接收缓冲清空（主站会把我们发出去的话组流量推回来，不清就会自激）。

### 13.3 ★ 60 秒空闲超时（必须加心跳）

这是本轮最容易踩的坑，实测数据：

```text
连上后什么都不发：  +60.2s 被 close(code=1006)
每 20 秒发一次订阅：120s 仍在线 ✓
```

也就是说**挂机守听时必定每 60 秒掉一次线**（没通话＝没数据＝算空闲）。
掉线重连的那一两秒正好有人开口，开头就丢了 —— 体验上就是「老是漏字」。

解法：`RW_KEEPALIVE_MS = 25000`，每 25 秒重发一次订阅报文当心跳
（订阅是幂等的全量替换语义，重复发没有副作用，不用另外造 ping）。
加完之后实测 150 秒连续在线、零断开。

### 13.8 「连上 → 发射一次 → 显示拒绝登录 → 重连」死循环

真机日志（2026-10-26 18:27）：

```text
18:27:26  RPTL→RPTACK, RPTK→RPTACK, RPTC→RPTACK → CONNECTED
18:27:30  开始发射 → 460 / 停止发射（两次，很短的 PTT）
18:27:36  主站返回 MSTNAK（当时状态 CONNECTED，登录 ID 8602553，端口 62031）
          → 断开重连 → 又连上 → 又 NAK …… 反复
```

#### 根因

**把「会话已建立之后」收到的 MSTNAK 当成了本次登录被拒。**

这类 NAK 几乎总是**上一次登录尝试留下的延迟报文**：握手阶段我们重发过 RPTL，
主站把重复的那一次判成「同 ID 第二次登录」回了 MSTNAK，UDP 延迟到达，
而此时我们早已握手完成、正连着。

旧代码一律当成「被同 ID 的另一台设备顶掉」→ 主动断开重连 → 重连又发 RPTL
→ 又制造一个延迟 NAK → **死循环**。用户看到的就是「连上、发射一次、然后显示拒绝登录」。

**判据**：主站真要踢掉一个**已建立**的会话，发的是 `MSTCL`，不是 `MSTNAK`。
（`MSTCL` 那条路本来就有，会正常自动重连。）

#### 修法

```java
// MmdvmSession.handle()
if (was == State.CONNECTED) {          // 三握手全过之后才到的 NAK
    lateNakCount++;
    log("收到一条延迟的 MSTNAK（会话已建立…），已忽略第 N 条");
    return;                            // 只记账，不动作
}
```

#### 代价与兜底

万一主站真把我们悄悄踢了，界面会一直显示「已连接」。用 MSTPONG 兜住：

- `pingLoop` 每 5 秒发 `RPTPING`，收到 `MSTPONG` 记 `lastPongMs`；
- 连续 **25 秒**（5 个 ping 周期）收不到 pong → 判定链路已断，主动重连；
- **只在本次会话收到过至少一个 pong 时才启用** —— 有些主站根本不回 MSTPONG，
  对它们做超时判断会变成每 25 秒自杀一次。

配套改动：

| 位置 | 改动 |
|---|---|
| `MmdvmSession` | 新增 `lastPongMs` / `lateNakCount`；首次收到 MSTPONG 打一条说明日志 |
| `DmrEngine` / `MainActivity` | 透传到 `dmrStatus()` 的 `pong` / `lateNak` 字段 |
| `dmr-listener.html` | 红牌判据从 `/MSTNAK/` 收紧成 `/连续\s*\d+\s*次拒绝/` —— 否则「延迟 MSTNAK（已忽略）」这条**正常**日志会把功能打成「暂不开放」 |

### 13.9 ESSID 别名被空串吃掉

日志里写 `登录 ID 8602553（未用别名）`，但界面上 ESSID 明明填着 `01`。

原因：`txLoad()` 把 localStorage 里的空串原样写回输入框，**覆盖掉 HTML 的
`value="01"` 默认值**。旧版本存过一次空串，之后每次加载都是空。
结果是登录 ID 退回裸 DMR ID —— 只要这个 ID 上已经有别的热点在线
（Pi-Star、另一台手机、上一轮没释放的会话），就会被判成重复登录。

修法：

```javascript
const es=txEl('txEssid');
if(es&&!String(es.value).trim())es.value='01';
```

**只处理「空」** —— 用户明确填 `0` 表示不用别名，那是他的选择，不动。

填 `01` 之后登录 ID 变成 `860255301`，与同一 Radio ID 上的另一台热点可以并存。

### 13.12 ★ ESSID 默认值错了：国际 BM 连不上的真正原因（第十一轮，2026-10-26）

真机日志（登录 ID 461418706 = Radio ID 4614187 + ESSID 06）：

```
→ RPTL  → RPTACK(salt)  → RPTK  → 31 秒无响应  → ERROR
状态：主站拒绝登录 ID 461418706（别名 06），停在 CONF 步
```

同一台机器上另一款客户端（截图）用**同一个 DMR ID、同一个密码**能连上，差别只有一处：

| | 本 App | 能连上的那款 |
|---|---|---|
| DMR ID | 4614187 | 4614187 |
| **ESSID** | **06** | **None** |
| 登录 ID | **461418706**（9 位） | **4614187**（7 位） |
| Callsign | 可能为空 | BH6RGQ |

#### 根因

主站在 **「下发配置」（RPTC）** 这一步做两件事：

1. 拿登录 ID 去查 SelfCare 里**有没有这条热点记录**；
2. 拿 RPTC 里的**呼号**去和该 DMR ID 注册的呼号**逐字符比对**。

本 App 两处都可能不匹配：

**① ESSID 默认给成了 `01`（错）。**
Pi-Star / DroidStar / BlueDV 这一项默认都是 `None`，SelfCare 里绝大多数人也只登记了
**裸 DMR ID 那一台热点**。默认 01 会让所有没动过这一项的人登录 ID 变成 9 位
（`461418701`），主站查不到这条记录 —— 密码那步还能过，配置这步必拒。
**这是默认值设计错误，不是用户填错。**

**② 呼号留空时拿 DMR ID 顶替（错）。**
`buildRptc()` 里写的是：

```java
String cs = callsign.isEmpty() ? String.valueOf(dmrId) : callsign;
```

呼号为空就发一串数字上去，主站比对必然失败 —— 而且日志只打「294 字节」，
完全看不出呼号到底发的是什么，这个原因被藏了很久。

#### 修法

**A. ESSID 改成下拉，默认 0（不用别名）**

```html
<select id="txEssid"></select>   <!-- 0 · 不用别名（默认） / 01~99 -->
```

`txLoad()` 的归一化也反过来了 —— 以前是「空值强推 01」，现在是「空值和非法值一律回落 0」：

```javascript
let v=parseInt(es.value,10);
if(!Number.isFinite(v)||v<0||v>99)v=0;
es.value=String(v);
```

**B. 呼号必填 + 自动大写**

```javascript
const call=txEl('txCall').value.trim().toUpperCase().replace(/\s+/g,'');
if(!call)return toast('请填呼号 —— 主站在配置阶段会核对呼号，留空必被拒');
```

大写是必须的：主站是逐字符比对，`bh6rgq` 和 `BH6RGQ` 算不匹配。

**C. RPTC 日志把关键字段打出来**

```
RPTC 配置串 294 字节（应为 294）｜呼号 BH6RGQ · 登录 ID 4614187（未用别名）· 软件 … · 硬件 …
```

呼号为空时额外打一条 `⚠` 警告。以后再出问题，一眼就能看出呼号/ID 发的是什么。

**D. 拒绝诊断的顺序整个调过来了**

以前的第①条是「换一个 ESSID 别名」—— **方向反了**。现在第①条是：

> 拿一台「现在能连上」的客户端对照它的 ESSID：显示 `None` 就把本 App 设回 0；
> 显示 `01` 才设成同一个值。

并且按阶段区分文案：`essid > 0` 时直接点明「你用的 9 位 ID 可能根本没登记」。

#### 一条通用经验

**别名不是万能药。** 之前几轮把「连不上」全归到「同 ID 第二台热点」上，
于是引导用户不断换 01/02/03…… 方向是错的：换得越多，越是在用一个主站不认识的 ID。
正确的第一步永远是**和一台能连上的客户端逐项对照**（ID / ESSID / 呼号 / 端口），
而不是加参数。

#### 验证

`_smoke_cn.js` 新增 7g 段 11 项（总计 **135 / 135**）：

- `#txEssid` 是 `<select>`、100 个选项、第 1 项值为 `0` 且文案含「不用别名」、第 2 项显示 `01`
- 存档里塞 `"abc"` → `txLoad()` 归一成 `0`；塞 `"77"` → 原样保留
- 呼号为空时 `txConnect()` **不调用** `Android.dmrConnect`（用探针替换原生接口验证）
- 填了呼号才真正发起连接
- `" bh6rgq "` → 传给原生的呼号是 `BH6RGQ`

APK dex 已确认含新文案：`拿一台「现在能连上」的客户端`、`RPTC 配置串`、
`呼号为空，本次用 DMR ID 当呼号发上去了`。

### 13.13 修完 ESSID/呼号后仍在 CONF 被拒：把诊断做到底（第十二轮，2026-10-26）

ESSID 默认值改 0、呼号必填两项上线后的真机日志：

```
[20:01:39] 声码器自检 9/9 全过
[20:01:52] 目标主站 43.129.83.124:62031（UDP），登录 ID 4614187
[20:01:52] RPTC 配置串 294 字节（应为 294）｜呼号 BH6RGQ · 登录 ID 4614187（未用别名）
           · 软件 BeaconDMR · 硬件 BeaconDMR_Android
[20:01:52] → 302 字节 [RPTC.Fh+BH6R] 52 50 54 43 00 46 68 2B 42 48 36 52 47 51 20 20 34 33 30 …
[20:01:52] ← 10 字节 [MSTNAK.Fh+] 4D 53 54 4E 41 4B 00 46 68 2B
[20:01:52] 主站返回 MSTNAK（第 1/5 次，当时状态 CONF，登录 ID 4614187，本机端口 62031）
[20:02:08] 手动改 ESSID 04 → 登录 ID 461418704 重试
```

#### 这份日志排除了什么

逐字节解包，配置串是**完全正确**的：

| 偏移 | 内容 | 判定 |
|---|---|---|
| 0–3 | `52 50 54 43` = `RPTC` | ✓ |
| 4–7 | `00 46 68 2B` = stream id | ✓ |
| 8–15 | `42 48 36 52 47 51 20 20` = `BH6RGQ␠␠` | ✓ 呼号 8 字节，右补空格 |
| 16–24 | `34 33 30 30 30 30 30 30 30` = `430000000` | ✓ 430.000000 MHz |

而且 **RPTK 已换回正常 RPTACK**（否则 `was` 会是 `AUTH`，不会是 `CONF`）。
所以可以确定地排除：

- ❌ 密码不对 —— RPTK 过了；
- ❌ 呼号为空/被数字顶替 —— 日志与十六进制都是 `BH6RGQ`；
- ❌ ESSID 默认值错 —— 登录 ID 已经是 7 位 `4614187`；
- ❌ 端口/协议/网络不通 —— 收到了主站回的包；
- ❌ 配置串结构错 —— 294 字节，字段宽度全对。

**剩下的只有一件事：主站认为「这个登录 ID + 这个呼号」不是它认识的那台热点。**
也就是说问题在**主站侧的登记信息**，或**我们和那台能连上的客户端之间还剩某个字段不一致**。

#### 本轮改的三处

**A. RPTC 全字段入日志**

以前只打「呼号 / 登录 ID / 软件 / 硬件」。现在配置串里每一个字段都打出来：

```
RPTC 配置串 294 字节（应为 294）｜呼号 BH6RGQ · 登录 ID 4614187（未用别名）
  · 收发频率 430.000000 MHz（收=发）· 时隙 1/1 · 色码不在本串内
  · 纬度 0.000000 · 经度 0.000000 · 类型 000 · 类型字符 '4'
  · 位置 "" · 描述 "BeaconDMR Hotspot" · url ""
  · 软件 BeaconDMR · 硬件 BeaconDMR_Android
```

目的很直接：**和「现在能连上的那台客户端」逐项对照**。
主站不会告诉你它嫌哪个字段不对（MSTNAK 只有 10 个字节，没有原因码），
唯一能做的就是把自己发出去的每个字段都摊开。

**B. 位置/描述/url 的非 ASCII 清洗**

MMDVM 配置串是**单字节定宽串**（位置 20 / 描述 19 / url 124，按字符数算）。
中文经 `ISO_8859_1` 编码会变成 `?` —— 不会撑破 294 字节（1 个中文 → 1 个 `?`），
但主站侧会显示成一串问号。原来的默认描述是 `信标 DMR 通联`，发上去就是 `?? DMR ??`。

改法两层：

```java
String loc  = toAscii(location, 20);
String desc = toAscii(description, 19);
String u    = toAscii(url, 124);
```

`toAscii()` 把 `0x20~0x7E` 以外的字符显式换成 `?` 并截断，字节数完全可预期；
同时打一条 `⚠` 告知用户「填的中文被替换了」。前端默认描述也改成 ASCII
`BeaconDMR Hotspot`，不再产生问号。

**C. CONF 被拒的文案直接写出「本次实际发了什么」**

```
本次实际发出去的是：登录 ID 4614187，呼号 BH6RGQ。上面 RPTC 日志已逐字段打印，可直接拿来对照。
```

并把排查清单第②条改成可执行的：

> 最快的核对办法：把「现在能连上」那台客户端里填的呼号**原样抄过来**；
> 或去 **radioid.net** 按 DMR ID 查注册呼号。

#### 给用户的排查路径（按顺序）

1. **BrandMeister Dashboard → Device Logs**，选中该 ID —— 主站会写明拒绝原因，这是唯一权威信息；

### 13.19 ★★ 找到真凶：ESSID 映射和 DroidStar 差一位（第十八轮，2026-10-26）

这一轮用户把「同样的配置能连上」的那个 APK 直接发过来了。逆向 + 对照源码之后，
**「同样的配置」这个前提本身就是错的 —— 两边填同一个数字，实际登录的是两个不同的 ID。**

#### 分析对象

| 项 | 值 |
|---|---|
| 包名 | `org.dudetronics.droidstar` |
| 版本 | versionName 1.0 / versionCode 89 |
| 体积 | 87.0 MB（199 个条目） |
| 技术栈 | Qt6 QML + 单个 `libDroidStar_arm64-v8a.so`（5.81 MB），只带 arm64-v8a |
| 许可 | GPL-3.0（`github.com/nostar/DroidStar`，作者 Doug McLain AD8DP） |

QML 源码以**明文**编译进 `libDroidStar_arm64-v8a.so`（`0x1a7fd4` 起），
配合 `assets/android_rcc_bundle.rcc`（只有 Qt 自带的 qmldir），可以直接读出界面逻辑。

#### 结论一：RPTC 配置串完全一致，不是报文格式问题

从 .so 里取出的格式串：

```c
"%-8.8s%09u%09u%02u%02u%8.8s%9.9s%03d%-20.20s%-19.19s%c%-124.124s%-40.40s%-40.40s"
```

逐字段对完：8+9+9+2+2+8+9+3+20+19+1+124+40+40 = **294**，
加 8 字节头（`RPTC` + 4 字节 streamId）= **302 字节**，`out.append(buffer, 302)`。

和我们发的**一字不差**：呼号 8、收/发频率各 9、slot 1/1、类型 `000`、类型字符 `'4'`。
纬度经度它用 `sprintf("%08f")` / `"%09f"` 先格式化成字符串再塞进 `%8.8s`/`%9.9s`，
我们直接给字符串 —— 都是空格填充，长度一致，主站不会因此拒绝。

**所以「配置串发错了」这条彻底排除。**

#### 结论二：★ ESSID 差一位，这才是「同样的配置」连不上的原因

`dmr.cpp:59`：

```cpp
void DMR::set_dmr_params(uint8_t essid, ...)
{
    if (essid){
        m_essid = m_dmrid * 100 + (essid - 1);   // ← 注意 -1
    } else {
        m_essid = m_dmrid;
    }
```

而 `SettingsTab.qml:205` 的下拉模型是：

```qml
var ids = ["None"];
for(var i = 0; i < 100; ++i){
    ids[i+1] = i.toString().padStart(2, "0");
}
```

即 `["None","00","01","02",…,"99"]`。于是：

| 下拉里选 | DroidStar 的 loginId | 我们（0-based）的 loginId |
|---|---|---|
| None / 00 | `4614187` | `4614187`（选 0） |
| 01 | `461418700` | `461418701`（选 1） |
| 03 | `461418702` | `461418703`（选 3） |
| **04** | **`461418703`** | **`461418704`（选 4）** |
| 99 | `461418798` | `461418799` |

**用户在 DroidStar 里选「04」，实际登录 `461418703`；在我们 App 里选「04」，
登录 `461418704`。这是两条完全不同的设备记录。**

而 BM 设备库里的事实是：

```
4614187    → MMDVM_MMDVM_HS_Hat / 438.5000 MHz   （真实硬件热点）
461418703  → MMDVM / 438.8000 MHz               （DroidStar 建的那条）
461418704  → 不存在
```

`461418703` 的频率 **438.8000** 正好等于 DroidStar 的默认值
`m_freq = "438800000"`（`droidstar.cpp:718`）—— 这条记录就是它连上去时建的，
所以 DroidStar 当然能连，我们发 `461418704` 当然被拒。

**13.16 节当时只知道「ESSID 04 不存在」，现在补上了最后一块：
用户以为自己在两边填的是同一个 04，其实不是。**

#### 结论三：其余实现差异（都不影响 CONF 阶段，但值得记）

| 项 | DroidStar | 我们 | 影响 |
|---|---|---|---|
| MSTNAK 处理 | 直接断开 + 10 秒后重连，**不分阶段** | 按阶段区分，CONF 被拒触发兜底查询 | 我们的更细 |
| 心跳间隔 | `m_ping_timer->start(5000)`，5 秒 | 按 60 秒空闲超时设计 | 都够用 |
| 默认频率 | `438800000` | 写死 `430_000_000` | BM 不校验，仅参考 |
| 默认 softwareId | `"20200922"` | `"BeaconDMR"` | BM 不校验 |
| 默认 packageId | `"MMDVM_MMDVM_HS_Hat"`（冒充真实硬件型号） | `"BeaconDMR_Android"` | BM 不校验 |
| 默认 url | `"www.qrz.com"` | 空 | 不影响 |
| 可选 RPTO | `m_dmropts` 非空时在 CONNECTED 后再发一个 `RPTO` 包 | 未实现 | 只影响热点的部分选项开关 |
| BM 密码 | 独立的 `BMPASSWORD` 设置项，优先于主机列表里的密码 | 单一密码框 | 我们的更简单 |

#### 本轮改的（不改映射，只消除歧义）

映射本身**保持 0-based 不动** —— 那才符合 BM SelfCare 的登记规则
（`DMR ID×100+ESSID`）。改的是「让用户看得见自己在用哪个 ID」：

**① ESSID 下拉每一项都印出实际登录 ID**

```

01 → 461418701
03 → 461418703
04 → 461418704
```

`txInitEssid(force)` 改成可重建，DMR ID 一改就重算（`#txId` 的 input 监听里调）。

**② 预检失败时直接说「该填几」**

以前只说「设备库里没有 461418704」，现在追加：

> → 把 ESSID 改成 **03** 就能对上 461418703。注意 DroidStar 的下拉比这里少 1：
> 它在 **04** 位拿到的也是 461418703

**③ 推荐哪一条要排序，不能直接拿第一条**

`found` 按 ESSID 升序排，第一条永远是裸 ID（ESSID 0）—— 而那恰恰是

### 13.22 ★ 最后一根稻草：经度字段多了一位小数（第二十一轮，2026-10-26）

13.21 的包装上去，日志显示 `sanitize` 生效了、参数已经和实测通过的那组完全一致：

```
· 收发频率 438.800000 MHz · 时隙 1/1
· 纬度 0.000000 · 经度 0.000000 · 类型 000 · 类型字符 '4'
· 软件 20200922 · 硬件 MMDVM_MMDVM_HS_Hat
→ 302 字节 RPTC …
← MSTNAK
```

**还是 MSTNAK。** 但同样的参数在我的 Python 测试里是 CONNECTED —— 说明还有一处字节不同。

#### 差异在经度

把 Java 的 `buildRptc()` 和测试脚本逐字段对：

| 字段 | App（Java） | 测试脚本 | 长度 |
|---|---|---|---|
| 纬度 `%8.8s` | `0.000000` | `0.000000` | 8 |
| **经度 `%9.9s`** | **`0.0000000`** | **` 0.000000`** | 都是 9 |

App 给的是 `"0.0000000"` —— **1 位整数 + 7 位小数，凑够了 9 个字符**，长度检查完全看不出问题。
测试脚本给的是 `"0.000000"`，经 `%9.9s` 右对齐补前导空格变成 `" 0.000000"`。

#### 实测确认

```
经度 " 0.000000"（9 宽右对齐）   → ✅ CONNECTED
经度 "0.0000000"（7 位小数）     → ❌ MSTNAK
经度 "0.0000000" + RPTL 重发 3 次 → ❌ MSTNAK
经度 "0.0000000" 复测            → ❌ MSTNAK
```

**主站按「整数位 . 6 位小数」的定长格式解析经度**，多一位小数就解析失败 → MSTNAK。
长度是 9、字面是合法浮点，肉眼和长度校验都看不出来 —— 这也是它能藏这么久的原因。

顺带验证：**RPTL 重发 3 次本身不影响结果**（修复后重发 3 次也 CONNECTED），
所以手机弱网时重发 RPTL 是安全的。

#### 修复

```java
/* 经度必须给 "0.000000"，让 %9.9s 自己右对齐补前导空格；
 * 写成 "0.0000000" 长度也是 9，但主站解析不出来 → MSTNAK */
cs, freqHz, freqHz, 1, 1,
"0.000000", "0.000000", 0,     // 原来经度是 "0.0000000"
loc, desc, '4',
u, swid, pkid);
```

#### 修复后实测

| 场景 | 结果 |
|---|---|
| 修复后 · RPTL 1 次 | ✅ CONNECTED |
| 修复后 · RPTL 重发 3 次（模拟弱网） | ✅ CONNECTED |
| 修复后 · 复测 | ✅ CONNECTED |
| 修复后 · ESSID 04（461418703） | ✅ CONNECTED |

**至此 BM 登录链路全部打通。** 三个真正的成因，按发现顺序：

1. **ESSID 映射差一位**（13.19/13.20）—— 填 04 会算成 `461418704`（不存在）
2. **softwareId / packageId 不合格**（13.21）—— 必须是合法日期 + MMDVM 型号
3. **经度多一位小数**（本节）—— 必须是 9 宽右对齐的 6 位小数

前两个会让「ID 或设备标识查不到」，第三个会让「配置串解析失败」，
三者表现完全一样（CONF 步 MSTNAK），所以只能靠原始报文逐字节对照才能挖出来。

### 13.23 登录通了之后：丢包优化三项 + 版本号（第二十二轮，2026-10-26）

用户实测反馈：**「连上了，通联了一次，有一定的丢包能优化吗？并且版本号要改变」**。
登录链路已经闭环，这一轮全部是链路质量与版本管理。

#### 丢包来源先分层，别一把梭

「丢包」在 MMDVM 链路上至少有三个互相独立的来源，表现都是「对方听我断字」或
「我听对方断音」，但修法完全不同：

| 层 | 症状 | 判据 |
|---|---|---|
| ① 麦克风采集 | 我方断字，但**网络统计里一个包都不丢** | 发送计数正常、接收侧 loss 0% |
| ② 发送 UDP 缓冲 | 弱网/切网瞬间整段丢 | 主站侧听感突变 |
| ③ 接收 UDP 缓冲 | 对方声音断，接收 loss 明显 | 序号跳变统计能看出来 |

原来的代码在这三层上都没有任何保护，也没有任何测量手段 —— 出了问题只能靠猜。
本轮补齐「测量 + 缓冲」两件事。

#### ① UDP 套接字缓冲：原来根本没设

Android `DatagramSocket` 默认接收缓冲往往只有 **64 KB**，按每包 55 字节、
60 ms 一包算，只能兜住不到 100 个包。任何一次系统卡顿（GC、后台切换、
省电调度）都可能让内核直接丢包。

```java
private static final int RCVBUF_BYTES = 512 * 1024;
private static final int SNDBUF_BYTES = 256 * 1024;

/** 给新建的套接字套上缓冲调优，并记录真实生效值 */
private DatagramSocket tune(DatagramSocket s) {
    int wantR = 0, wantS = 0, gotR = 0, gotS = 0;
    try { s.setReceiveBufferSize(RCVBUF_BYTES); wantR = 1; } catch (Exception ignored) { }
    try { s.setSendBufferSize(SNDBUF_BYTES); wantS = 1; } catch (Exception ignored) { }
    try { gotR = s.getReceiveBufferSize(); } catch (Exception ignored) { }
    try { gotS = s.getSendBufferSize(); } catch (Exception ignored) { }
    if (wantR == 1 || wantS == 1) {
        log("UDP 缓冲：收 " + (gotR / 1024) + " KB · 发 " + (gotS / 1024) + " KB"
                + "（申请 " + (RCVBUF_BYTES / 1024) + "/" + (SNDBUF_BYTES / 1024) + " KB）");
    }
    return s;
}
```

`openSocket()` 里 4 个 `return s;`（直连、绑定 62031、绑定失败回退等分支）
**全部改成 `return tune(s);`** —— 漏掉任何一个分支，那条路径就等于没优化。

日志里会打出**实际生效值**：部分 ROM 会把申请值截到 `net.core.rmem_max`，
所以「申请 512 KB、实际 128 KB」这种信息必须能看到，否则没法判断调优有没有落地。

#### ② 采集缓冲：8 帧 → 32 帧

发送是**采集驱动**的：每读满 3 帧（60 ms）就编一包发出去。编码本身要占几毫秒，
系统调度、GC、后台任务都可能把这一轮拖到几十毫秒。原来只给了 8 帧（160 ms）：

```java
// 原来
int bufBytes = Math.max(minBuf, FRAME_SAMPLES * 2 * 8);
// 现在
int bufBytes = Math.max(minBuf, FRAME_SAMPLES * 2 * 32);   // 640 ms
```

缓冲薄于停顿，`AudioRecord` 内部就会覆盖未读数据 —— 丢的是**麦克风侧**的样本。
这种丢包在网络统计里一个包都不会少，最难查，所以宁可多给缓冲。
代价只是发射链路的启动延迟从 ~160 ms 变成 ~640 ms，通联完全无感。

#### ③ 接收丢包统计：靠 DMRD 序号跳变算

DMRD 包第 5 个字节（`buf[4]`）是 8 位循环序号，主站每 60 ms 加一。
差 1 = 正常，差 0 = 重复包，差 2~63 = 中间丢了 `差-1` 个，
差得离谱（≥64）多半是换话组或重连，重置基线不累加：

```java
if (len == 55 && startsWith(buf, len, "DMRD", 4)) {
    int seq = buf[4] & 0xFF;
    if (dmrdSeqLast >= 0) {
        int gap = (seq - dmrdSeqLast) & 0xFF;
        if (gap == 0) {
            /* 重复包，不算丢 */
        } else if (gap < 64) {
            dmrdLostCount += (gap - 1);
        } else {
            dmrdReorderCount++;
        }
    }
    dmrdSeqLast = seq;
    dmrdRxCount++;
    ...
```

对外三个方法：

```java
public String getRxStats()          // "收 1200 包 · 丢 7 包（0.6%）"
public double getRxLossPercent()    // 0.58
public long   getRxPacketCount()    // 1200
```

**会话重置时必须一起清零**（`connectInternal()` 的重置块）：

```java
dmrdSeqLast = -1;   // ← 这个尤其重要
dmrdRxCount = 0;
dmrdLostCount = 0;
dmrdReorderCount = 0;
```

`dmrdSeqLast` 若留着上一轮的序号，新会话第一个包会被算成「跳了 N 个」，
凭空多出一堆丢包 —— 统计值会直接失真。

#### 界面上怎么用

「发射」页 → 接收卡片里新增一行 **链路质量**，每 2 秒从 `Android.dmrStatus()`
读一次（累计值，读太勤只是白白跨 JS↔Java 桥）：

- 未连接显示 `—`，不留上一轮的旧数字
- 丢包率 ≥ 3% 时标红（`#txRxStats.warn`）

排障顺序：**先看这个数字**。如果是 0% 但对方说你断字，问题在麦克风侧（第 ②
项）；如果数字明显，问题在网络侧（第 ① 项），可以再把「接收缓冲」往上拉。

断开时还会往日志里写一行「本轮接收质量（用户断开）：收 N 包 · 丢 N 包（x%）」，
方便通联结束后回看这一轮到底怎么样，不用一直盯着设置页。

#### 顺手修掉的一个静默 CSS 失效

写这一行时发现 `.ptxst.bad{color:var(--bad)}` 一直**没有生效**：调色板里
只有 `--tx`（红）、`--ok`（绿）、`--warn`（橙），**根本没有 `--bad` 这个变量**。
`var(--bad)` 解析失败时该声明在「计算值阶段」整条作废，于是 `.bad` 状态只剩
加粗、颜色照旧 —— 界面上看着像生效了，其实没变红，而且不会报任何错。

补上变量即可，浅色/深色各一份：

```css
:root{ --bad:#c22a2f; }                       /* 比 --tx 深一点，白底小字更清楚 */
html[data-theme="dark"]{ --bad:#ff7b80; }
```

**教训**：`var(--x)` 引用不存在的变量是静默失效，不报错、不进控制台，
只能靠「取 computedStyle 看颜色」这种笨办法验证。CSS 改完必须实测计算值。

```java

```

### 13.24 接收过滤：多路混音 + 呼号屏蔽（第二十三轮，2026-10-26）

用户反馈两件事：

> 通联的时候存在有可能多个订阅的声音传过来，还有就是能否增加设置某个呼号过滤，
> 就是设置之后通联的时候过滤的那个呼号的音频不接受

这是两个独立的问题，只是都会表现成「听不清」。

#### 问题一：多路语音混进同一个抖动缓冲

接收链路只有**一条**抖动队列（`DmrAudio.queue`）。主站会把你订阅过的每个话组都推
过来 —— SelfCare 里设成静态话组的常推，PTT 说过话的话组动态激活十分钟也推。
两路同时到达时，`DMRD` 包是交替插入同一个队列的，解出来的 PCM 就一帧这人、
一帧那人，听起来像**几个人同时说话**，谁也听不清。

这不是丢包，也不是解码错误，`链路质量` 会显示 0% —— 只看数字会误判成网络很好。

**修法：单流锁定**（`DmrEngine.onDmrd`）。

```java
long now = System.currentTimeMillis();
boolean same = (srcId == lockSrc && dstId == lockDst && slot == lockSlot);
if (!same) {
    boolean free = (lockSrc == 0) || (now - lockAtMs > STREAM_HOLD_MS);
    /* 抢断权：自己关注的话组，或者点名呼我的个呼 */
    boolean preempt = forMe || (txDstId > 0 && dstId == txDstId);
    if (!free && !preempt) return;      // 正在听的那路还没说完，别的路先等着
    if (preempt && !free) audio.flush(); // 抢断要把旧流残余清掉，否则会叠在一起
    lockSrc = srcId; lockDst = dstId; lockSlot = slot;
}
lockAtMs = now;
```

- `STREAM_HOLD_MS = 400`：比抖动缓冲的 `GAP_MS`（360 ms）略长。太短会在同一句的
  换气间隙被别的流抢走，听感是「半句就断了」；太长则别人插话要等半天。
- **个呼必须放行**：`dstId == myId` 说明有人专门呼叫我。这条规则如果漏了，
  「只收当前话组」一开就会连点名都听不见 —— 这是最容易写错的地方。
- **关注的话组有抢断权**：别人占着麦时，自己话组一来立刻切过去，不用等 400 ms。

配套新增 `setWatchTg(int)`：界面选好话组就同步给原生侧，**不用等第一次 PTT**。
否则「刚连上、还没发过话」那段时间，别的静态话组照样挤进来。

#### 问题二：按呼号屏蔽

##### 为什么过滤只能按 ID 做

`DMRD` 包里**只有源 ID，没有呼号**：

```
DMRD(4) + seq(1) + src(3) + dst(3) + rpt(4) + flags(1) + streamId(4) + payload(33)
                   ↑ 只有这三个字节是「谁在说」
```

呼号得靠外部库反查。如果按呼号过滤，就得**每 60 ms 查一次库** —— 不可能。
所以设计成：

- 名单里显示「呼号 + ID」，**实际比对的是 ID**
- 填呼号时先查本地库（国内台站库 `CN.byCall` / 实时流缓存 `state.idCache`），
  查不到再让原生侧打一次 RadioID.net 换成 ID —— **只查一次，结果存下来**
- 查不到呼号也不影响使用，直接填 ID 一样能屏蔽

##### 屏蔽在链路最前端生效

```java
java.util.Set<Integer> block = rxBlock;
if (!block.isEmpty() && block.contains(srcId)) {
    rxBlockedCount++;
    if (srcId != rxBlockedLastSrc) {        // 同一个人连着说话只提示一次
        rxBlockedLastSrc = srcId;
        emit("blocked", "srcId", srcId, "dstId", dstId);
    }
    return;                                  // ← 连解码都不做
}
```

放在最前面有三个好处：不解码（省 CPU）、不占抖动缓冲（否则「屏蔽了还是卡」）、
不影响丢包统计的语义。`rxBlock` 用**不可变集合整体替换**而不是原地增删 ——
接收线程在读的同时界面线程可能在改，整体替换天然没有并发问题。

##### 呼号查询为什么必须在原生侧做

页面跑在 `https://appassets.androidplatform.net`（真实 https 源，为了 localStorage
能用的既定设计），所以 `fetch` 跨域要过 CORS。实测三个源：

| 源 | `Access-Control-Allow-Origin` | 能否在页面里 fetch |
|---|---|---|
| `api.brandmeister.network` | 回显 Origin | ✅ 可以 |
| `860.radiowo.com` | `*` | ✅ 可以 |
| `database.radioid.net` | **没有这个头** | ❌ 被浏览器拦掉 |

所以查询放 Java 侧（原生 HTTP 没有 CORS）：

```java
@JavascriptInterface
public void dmrLookupDmrIdAsync(final String q) {
    new Thread(() -> deliverLookup(DmrDirectory.lookup(q)), "dmr-lookup").start();
}
```

**必须异步**：桥接方法跑在 WebView 的 JavaBridge 线程上，同步阻塞会把 JS 一起卡住
（页面在等返回值），弱网下就是几秒白屏。查完用 `evaluateJavascript` 回抛给
`window.__dmrLookup(res)`，`res` 形如 `"4614187|BH6RGQ"`，空串表示没查到。

RadioID.net 接口不需要 key（响应头只有一句 `X-RadioID-API-Key: recommended`），
两个方向都支持：

```
https://database.radioid.net/api/dmr/user/?callsign=BH6RGQ   → results[].id
https://database.radioid.net/api/dmr/user/?id=4614187        → results[].callsign
```

查不到时返回 `{"count":0,"results":[]}`，不是 404 —— 解析时按空数组处理即可。

##### 界面

「设置 → 发射」折叠里新增 **🚫 接收过滤** 卡片：

| 控件 | 作用 |
|---|---|
| 只收当前话组（开关，默认开） | 单流锁定的总闸 |
| 屏蔽呼号（输入框 + 添加） | 接受呼号或纯数字 ID，回车也能提交 |
| 已屏蔽（chip 列表） | 每项带 ×，点了取消屏蔽；标题右侧显示「已挡掉 N 包」 |
| 最近听到（chip 列表） | 通联时自动积累，**点一下就屏蔽** —— 比手打呼号可靠 |

「最近听到」是从已有的 `rx` 事件里攒的（原生侧本来就在句子边界上报 srcId/dstId），
不需要新增事件，也不持久化 —— 那是一次会话的现场信息，存下来没意义。

##### 踩坑记录

- **`log()` 是 `MmdvmSession` 的方法，`DmrEngine` 里没有** —— 直接调用编译不过，
  要用 `emit("log","line",...)`。
- **页面启动时会无条件推一次名单**，如果每次都打日志，每进一次 App 就多一条
  「接收屏蔽名单：空」的噪音。所以 `setRxBlock` / `setRxOnlyWatchTg` 都加了
  「内容没变就直接 return」。

### 13.25 话组静音 + 三个「只能重启」的 bug（第二十四轮，2026-10-27）

用户报了四件事，其中三件是 bug，而且**症状都能用「重启 App 才好」概括**。
这一类问题的共同点：某条后台线程悄悄死了，界面却还在照常显示。

#### ① 话组单独静音

和「屏蔽呼号」是两个维度：

| | 按什么判 | 典型场景 |
|---|---|---|
| 屏蔽呼号 | 谁在说（`srcId`） | 某人一直插话 |
| **静音话组** | 在哪个组说（`dstId`） | 某个组一直有人闲聊，但你还想留在这个组上 |

静音的话组**照样能往里发**，只是不再出声 —— 这是和「取消订阅」的本质区别。

实现在 `onDmrd` 里，顺序是「屏蔽呼号 → 静音话组 → 只收当前话组 → 单流锁定」：

```java
java.util.Set<Integer> mute = rxMuteTg;
if (!forMe && !mute.isEmpty() && mute.contains(dstId)) {
    rxMutedCount++;
    return;
}
```

`forMe`（`dstId == myId`）不受话组静音影响 —— 那不是组呼，是有人点名呼我。

界面沿用「点一下就生效」的 chip 模式：**最近话组**列表从 `rx` 事件里攒
（和「最近听到」同源），点一下静音；也可以手填话组号。

#### ② 接收线程一死，只能重启

`rxLoop` 原来这么写：

```java
} catch (IOException e) {
    if (!running) break;
    if (socket != s) continue;
    log("接收异常：" + e.getMessage());
    break;                    // ← 问题在这里
}
```

**同一个套接字抛 IOException 就 break，接收线程直接退出。** 会走到这里的场景很常见：
Wi-Fi 与移动数据互切、NAT 映射被回收、低内存下系统回收 fd、飞行模式开关一次。

后果是连锁的，而且每一环都像独立故障：

1. 收不到 `MSTPONG` → 25 秒后判定「心跳超时」→ 去重连
2. 重连时套接字可能是复用的，**接收线程却已经是死的** → 重连也收不到东西
3. 界面显示「已连接」，但既没有语音也没有心跳

用户看到的就是「有人正在通联但没声音，只能重启」+「待机时莫名心跳超时重连」。

修法：**重建套接字继续循环，绝不 break**。丢几个包远比线程死掉轻。

```java
log("接收异常：" + e.getMessage() + " —— 重建套接字后继续（接收线程不退出）");
try { restartSocket(); } catch (Exception ignored) { }
if (!sleepQuiet(200)) break;
continue;
```

再加一层兜底 `ensureRxThread()`：`pingLoop` 每 5 秒查一次接收线程是否还活着，
死了就原地拉起来（不影响当前登录状态）。

#### ③ 播放线程和音频上下文同样会「静默死亡」

**原生侧（通联音频）**：`DmrAudio.loop()` 原来没有顶层 try。任何异常
（`AudioTrack` 构造、`listener` 回调、数组越界）都会把线程带走 —— 队列只进不出，
界面停在「正在接收」，永远没有声音，且不报任何错。

修法三条：

1. 循环体整体包 try/catch，异常后复位（`stopPlayback` + 清队列）继续
2. 每帧检查 `AudioTrack.getPlayState()`，不是 `PLAYSTATE_PLAYING` 就重建 ——
   来电、音频焦点被抢、蓝牙切换、音频 HAL 重启都会让它**悄悄停掉**，
   此时 `write()` 往往仍返回成功但不出声
3. `write()` 返回负值也当失效处理

顺带修掉一个隐藏 bug：`startPlayback()` 里 `for (short[] f : prefill) writeFrame(f);`
—— 现在 `writeFrame` 可能调用 `stopPlayback()` 清空 `prefill`，边遍历边清会抛
`ConcurrentModificationException`。改成先 `toArray` 快照、清空、再遍历。

**网页侧（收听音频）**：`Audio_.play()` 原来只在 `ready` 时直接排音源，
从不检查 `AudioContext.state`。一旦上下文被挂起（来电、焦点被抢、熄屏、蓝牙切换），
后面 schedule 出去的音源**全部不会出声**，但数据照收、`#nowbar` 照旧显示
「有人在通联」。这就是用户说的「上方显示有人正在通联但语音没反应」。

修法：`play()` 每次自查状态，挂起就 `resume()`；另外每 3 秒跑一次 `audioGuard()`。
重启 App 能好，本质就是重建了 AudioContext —— 现在不用重启了。

#### ④ 切网络后第一次发射没反应

`setNet()` 原来只关了收听链路（Hoseline / radiowo 的 WebSocket），
**完全没动 MMDVM 会话**。而国际 BM 和国内 China DMR 是两台不同的主站：
不同域名、不同 DMR ID 号段、不同热点密码。

所以切网络后：界面参数已经换成新网络，会话却还挂在旧主站上。按 PTT 时 DMRD
发往旧主站，而你要的话组在新主站上根本不存在 —— 表现就是「第一次发射没反应，
得手动断开再重连」。

修法：切换前如果连着，先主动断开，切完自动用新身份重连：

```js
const wasConn = TX.conn || TX.state==='CONNECTING' || TX.state==='AUTH' || TX.state==='CONF';
if (wasConn) { Android.dmrDisconnect(); ... }
// ...切完、载入新身份...
if (wasConn) setTimeout(()=>{ if(!TX.conn) txConnect(); }, 900);
```

**为什么要等 900 ms**：主站对同一个 Radio ID 只允许一个会话，断开（RPTCL）和
登录（RPTL）贴太近会被判成「上一个还没退干净」而回 MSTNAK。

#### ⑤ 心跳超时判定改用「连发几个 ping 没回」

原来用墙上时钟：

```java
long silence = System.currentTimeMillis() - lastPongMs;
if (silence > PONG_TIMEOUT_MS) { /* 判定链路已死 */ }
```

**熄屏后系统会冻结进程**（Doze / App Standby / 厂商省电），ping 线程几秒到几分钟
跑不到。一恢复运行，算出来的「沉默时长」早就超过 25 秒 —— 明明链路好好的，
却被判定「心跳超时」去重连。这就是「待机时莫名提示心跳超时正在重连」。

改成数「发了几个 RPTPING 还没换回 MSTPONG」：

```java
private static final int PONG_MISS_LIMIT = 5;   // 5 × 5s = 25s

send(ping);
pingsSincePong++;
if (lastPongMs > 0 && pingsSincePong >= PONG_MISS_LIMIT) { /* 真的断了 */ }
```

进程被冻结时计数不会增长，只有**真的发了 5 个 ping 都没回应**才判定断开 ——
免疫调度延迟，语义也更准确。

### 13.26 设置页折叠 + 内边距对齐的坑（第二十五轮，2026-10-27）

设置页原本有 12 张卡片全部展开，手机上要滑三四屏才能从「外观」翻到「关于」，
找一项得从头拖到尾。改成**手风琴**：默认只留标题一行，点标题才展开，
展开状态按卡片 id 记在 `localStorage.setItem('setOpen')` 里。

#### 为什么「不搬 DOM」

最直觉的写法是把标题以下的内容包进一个 `div`，再对这个 `div` 做 display 切换。
**不行** —— 卡片里有绝对定位的面板（主站选择下拉列表）和需要溢出显示的
`#txFoldBody`，多包一层就会被 `overflow` 裁掉。所以只加 class，靠兄弟选择器隐藏：

```css
.setwrap .foldable:not(.open) > *:not(h3){display:none}
```

标题本身必须留在 DOM 里（不然没法点开），所以用 `:not(h3)` 排掉它。

#### 跳过已经有折叠机制的卡片

「⚙️ 主站与身份」这张卡片在 13.x 之前就有自己的 `#txFold` / `#txFoldBody`，
如果被外层手风琴再包一次会变成两层折叠、点一下只开一层，用户会以为坏了。
`setFoldInit()` 里用两个条件跳过：

```javascript
if(card.querySelector(':scope > .foldbody')||h.classList.contains('foldh'))return;
```

`:scope >` 是关键 —— 不加的话会匹配到子孙里的 `.foldbody`（比如「接收过滤」
卡片内部并没有，但「通联（MMDVM）」卡片里有嵌套结构），误判成「自带折叠」。

#### ★ 内边距放错地方 = 展开后整块错位

用户报的原话是「接受过滤这一项点开之后显示不对」。CDP 量出来的数据是：

| 元素 | 左边缘 |
|---|---|
| `h3` 文字 | 31px |
| `#txRxBlockIn`（输入框） | **1px** |

差了 14px。原因是两套约定打架：

- `.txcard` 本身 **0 左右内边距**，里面的 `.rxrow` / `.blockwrap` / `.txnote` 也是 **0**，
  全靠 `h3` 自己的 `padding:11px 14px` 撑出视觉缩进；
- 卡片一旦有了背景和边框，内容就贴着边框画，标题却缩进 14px。

修法是**把内边距放到卡片上，再用负外边距把标题拉回满宽**：

```css
.setwrap .txcard{margin-bottom:0;padding:0 14px 12px;overflow:visible}
.setwrap .txcard > h3{margin:0 -14px;padding:11px 14px}
.setwrap .txcard > .foldbody{padding:12px 0 2px}
```

负外边距是必须的：标题的底色（`--panel2`）和分隔线要画到卡片边缘，
不能被 14px 的内边距裁在中间。实测输入框从 `l:1` 变成 `l:15`，
`h3` 文字左边缘 31px、所有内容块左边缘 31px，对齐。

⚠ `overflow:visible` 也不能少 —— 见上面「不搬 DOM」那条。

#### 顺手修的几处

| 位置 | 问题 | 修法 |
|---|---|---|
| `#txRxMuteIn` | 窄屏定宽 100px + 按钮 `margin-left:auto`，中间空出一大截 | 改 `flex:1 1 auto`，按钮自然贴右 |
| `.portrow` | 窄屏 `padding:9px 11px`，比同卡片的文字靠左 3px | 改 `9px 14px` |
| `.foldh .foldico` | 11px + `--dim`，比手风琴的箭头更淡，看着像没箭头 | 统一成 12px + `--muted` + `flex:none` |

#### 验证方式

`_diag_sweep.js` 逐张展开每个折叠卡片，对**每个带直接文字的子元素**算
`rect.left + paddingLeft`（不是 `rect.left`，否则 `.setcard` 那种「行自带 14px」
的写法会全是误报），与 `h3` 的文字左边缘比对；同时检查
`rect.right > cardRect.right` 和 `scrollWidth > clientWidth`。
390 / 820 两个宽度下 11 张卡片全部 0 问题。

### 13.27 首页上下分区 + PTT 可拖动 + 波形不再被隐藏（第二十六轮，2026-10-27）

这一轮改了首页的信息架构，顺带修了两个「显示不全」的老问题。

#### ① 首页改成「上下分区」

原来 `#viewListen` 是「网络条 → 发射条 → 三栏列表（我的/活动/库）→ 悬浮 PTT」一条直线，
手机上要滑很久才能在列表和 PTT 之间来回。现在改成两块：

| 区域 | 内容 | 行为 |
|---|---|---|
| 上半屏 `.home-top` | 网络切换 + 发射条 + PTT 操作区 | `position:sticky` 钉在顶栏下方，不随列表滚走 |
| 下半屏 `.home-list` | 可切换列表（我的收听 / 实时活动 / 话组库） | 正常滚动 |

关键点：

- **`.home-top` 用 sticky 而不是固定高度 + 内部滚动**。后者要把 `body` 改成
  flex 列、让 `#viewListen` 撑满视口，会波及看板/设置两个视图，风险太大。
  sticky 只需一行 CSS，PTT 照样一直在视野里。
- **`--htop-h` 实测喂给 CSS**。操作区高度随宽度换行而变（发射条会折行），
  `mobnav` 要钉在它正下方，写死数值必然错位。`syncHomeTopH()` 把
  `.home-top` 的 `offsetHeight` 写进 CSS 变量，`mobnav` 用
  `top:calc(var(--topbar-h) + var(--htop-h))` 跟随。
- **合并底色**。操作区里 `.netbar` / `.ptx` 原本各自带 `background:var(--panel)`
  和 `border-bottom`，并进 `.home-top` 后会出现双层分隔线，所以统一改成透明、
  只由 `.home-top` 出一层底和一条分隔线。

#### ② PTT 可拖动（设置开关控制）

用户选的是「设置里开关」而不是「长按进入拖动」——因为 PTT 本身是**按住说话**，
和拖动天然冲突。最终用「开关 + 双闸判定」解决：

| 手势 | 判定 | 结果 |
|---|---|---|
| 按住后移动 > 6px | 拖动 | 挪位置，**绝对不发射** |
| 按住 ≥ 180ms 不动 | 长按 | 开始发射，松手停 |
| 按住 < 180ms 松手 | 点按 | 发一段 250ms 短发射 |

实现要点：

```javascript
// pointerdown 起一个 180ms 定时器；一旦 move 超过阈值就 clearTimeout 并进入拖动
pttTimer = setTimeout(()=>{ pttTimer=null; if(pttArmed&&!pttDragging) txPttDown(e); }, 180);
```

- 拖动时用 `setPointerCapture`，手指滑出按钮也继续跟手；
- 位置夹在视口内（`pttClamp`），存 `store.set('pttPos',{x,y})`；
- 开开关才加 `.draggable`（描边 + `cursor:grab`），关掉 `pttApplyState()`
  清掉 `position/left/top` 让它回到操作区中央；
- 失焦时强制 `txPttUp()` 并清挂起状态，避免卡在「按住」。

⚠ **PTT 尺寸其实被 `.ptt` 覆盖了**：`.ptt{width:148px}` 写在文件更后面，
同权重下压过前面的 `.pttf{84px}`，实测手机 132px（`.ptt` 的窄屏覆盖）、
桌面 148px。所以它是「大圆钮」而不是设计注释里写的 82px。这次没动尺寸，
只保证它在操作区里放得下（操作区宽 140px 时钮 132px）。

#### ③ 语音波纹「不能完全显示」

根因是 `@media(max-width:420px){ .vu{display:none} }` —— **窄屏直接把
`#vu` 那 16 根 VU 条整个隐藏了**。改成缩小显示：

```css
@media(max-width:420px){ .vu{order:4;width:56px;height:22px} }
```

`renderVu()` 的渲染逻辑没动：静音时 16 根条都是 3px（一条淡淡的底线），
有声音时按电平长到 9~22px 并变色。所以「看得到波形」和「静音时是平的」
两者都对。

#### ④ ★ 电平条把提示文字盖住了（自己挖的坑）

改成 `.home-top .ptx{padding:0}` 去掉内边距后，发射条底部那行提示
（「先连接主站，再按住 PTT 说话」）最后一行被一条**白色圆角长条**盖住，
看起来像「文字被裁掉了」。查下来是 CSS 层叠问题：

```css
.ptxm{height:3px;border:0;border-radius:0}   /* 第 147 行 */
.meter{height:10px;border-radius:99px;...}   /* 第 536 行 —— 在后面，赢 */
```

`.meter` 和 `.ptxm` 同权重（都是单个类），后出现的 `.meter` 胜出，于是本该
3px 的细线变成 10px 圆角胶囊，`position:absolute;bottom:0` 正好压在提示文字上。
修法两处：

```css
.meter.ptxm{height:3px;border:0;border-radius:0;background:var(--panel2)}
.home-top .ptx{padding:0 0 6px}   /* 给 3px 电平条留出位置 */
```

**教训**：写组件变体时，如果基础类定义在变体之后，必须用复合选择器提权重
（`.meter.ptxm`），否则「变体」根本生效不了，而且不报错。

#### ⑤ 顶部「收听」改名「主页」

- 导航 tab：`🎧 收听` → `🎧 主页`（`data-view="listen"` 不变，只改文案）
- 窄屏播放按钮短标签：`🔊 收听` → `🔊 听`（避免和导航标签撞名）
- 宽屏播放按钮仍是「🔊 开始收听」——它是**动作**（开始/静音），不是页面名，
  所以没跟着改

### 13.28 首页三连修 + 操作区手动折叠（第二十七轮，2026-10-27）

上一轮把首页改成「上下分区」之后，暴露出三个连锁问题，外加用户新提的折叠需求。
这一轮全部落在 `dmr-listener.html` 的 `.home-top` / `.home-list` 这一小块上。

#### ① 分栏条与操作区之间露出一条缝

分栏条 `#mobNav` 原本是**独立**的 sticky，靠 `top:calc(var(--topbar-h) + var(--htop-h))`
算出来的偏移去对齐操作区下沿。`--htop-h` 是 JS 实测喂进去的，但实测发生在**渲染之后**：
只要发射条的提示文字换行/不换行切换一次（比如连上主站后提示从「先连接主站…」变成
「已连接 · 主站 xx」），操作区高度就变了，分栏条却还按旧偏移钉着，中间露出 10~20px 的缝。

**修法**：把 `mobNav` **搬进** `.home-top` 内部，两者共用一个 sticky 容器：

```css
.mobnav{position:static;background:transparent;border-bottom:none}
```

同一个容器里用 `gap` 排版，中间不可能有缝 —— 这不是「算得更准」，而是「不用算」。
`--htop-h` 保留着（`syncHomeTopH()` 还在写），只是分栏条不再依赖它。

#### ② ★ 滚到中间时顶栏空了、操作区悬在半空

用户描述：往下滑，一开始顶部模块跟着一起走，滑到中间时顶部的模块变空了，
网络切换条和分栏条「悬在中间」。

根因是**包含块**，不是 z-index：

```css
html,body{height:100%}   /* ← 错 */
```

`body` 被钉成「一个视口高」之后，它就成了 `.topbar`（`position:sticky`）的**包含块**。
sticky 元素只能在包含块范围内滑动 —— 页面滚过 `视口高 - 顶栏高` 之后，顶栏就走到了
包含块底边，**脱粘被滚走**。而 `.home-top` 的包含块是内容很高的 `#viewListen`，
还老老实实钉在 `top:68px`。于是：顶栏那块**空了**，网络条和分栏条**悬在半空**。

实测（820×1000，滚到 2000px）：修前 `topbarTop: -224`、`htTop: 68`；
修后 `topbarTop: 0`、`htTop: 68`，两者一起粘住。

```css
html{height:100%}
body{min-height:100%}    /* ← 对：body 随内容长高，和 #viewListen 一样高 */
```

一行 `height` 改 `min-height`，症状全部消失。这个坑很隐蔽，因为页面**能滚**、
顶栏**前半程也正常**，只有滚过一屏才开始错位。

### 13.29 开源归档：目录重构 + 版权声明合规（第二十八轮，2026-10-27）

散落的源码整理成可开源的仓库结构，顺带解决一个**法律上的硬冲突**。

#### ① 版权声明和 GPL 打架

界面页脚原文：

> 界面与外观设计 © 2026 BH6RGQ，保留所有权利。未经许可请勿复制或用于衍生作品。

但项目移植了 DroidStar（GPL-3.0）的发射逻辑、MMDVMHost（GPL-2.0+）的 FEC，
还分发了 droidstar_vocoder_plugin 的二进制。**GPL 是传染性的**，整个程序必须以
GPL-3.0 分发；而 GPL 第 2 条明确授予「复制和衍生」的权利。
「保留所有权利 / 请勿复制」与它**直接矛盾** —— 开源出去就是一个自相矛盾的许可声明。

改成：

> 开源项目 · 代码以 GPL-3.0 发布 · 界面设计署名 BH6RGQ

设置页的「关于」同步改成「本项目以 GPL-3.0 开源发布，可以自由使用、修改与再分发，
条件是保留同样的开源许可与作者署名」。署名权保留，与 GPL 不冲突。

#### ② 归档结构

原来所有东西平铺在一个中文目录里，APK 产物、临时诊断脚本、源码混在一起。
现在按开源仓库的惯例分层：

```
beacon-dmr/
├── web/dmr-listener.html     前端唯一真源
├── android/                  Gradle 工程（含 cpp / java / jniLibs）
├── third_party/              声码器插件原件 + 接口头
├── tools/                    构建 / 数据生成 / APK 校验
├── tests/                    冒烟测试 + 静态检查
├── docs/                     实现说明 / 决策备忘 / 逆向笔记 + 截图
├── README.md  LICENSE  THIRD-PARTY.md
└── .gitignore  .gitattributes
```

`assets/index.html` 不再单独维护 —— 它是 `web/` 的副本，构建时由脚本同步并
逐字节校验。仓库里只有一份真源，避免「改了 A 忘了 B」。

#### ③ 密钥绝对不能进仓库

`beacon-dmr.jks`（签名密钥）和 `keystore.properties`（明文口令）都排除了。
**密钥一旦泄漏，任何人都能签出可覆盖安装的更新包**，等于丢了这个包名的发布权。

`app/build.gradle` 原本就有 `hasKeystore` 判断，缺 `keystore.properties` 时
自动跳过签名，所以别人 clone 下来照样能构建（产出未签名包）。
另外给了 `keystore.properties.example` 说明怎么生成自己的密钥。

#### ④ `.gitattributes` 锁死换行符

这个项目有两处对换行符敏感：

1. `build_apk.sh` 用 `cmp -s` 逐字节比对 `web/` 和 `assets/` 的 HTML，
   两边换行不一致就直接判定失败
2. `gradlew` / `*.sh` 带 CRLF 在 Linux、macOS 上**根本执行不了**

Windows 上 `core.autocrlf` 默认会把 LF 转成 CRLF，所以显式写了：

```gitattributes
* text=auto eol=lf
*.bat text eol=crlf
*.so binary
*.jar binary
```

`git ls-files --eol` 验证：`gradlew` 和 `build_apk.sh` 索引与工作区都是 `lf`，
`.so` 是 `-text`（二进制）。另外给 `gradlew`、`build_apk.sh` 补了可执行位
（`git update-index --chmod=+x`），否则 Linux 上 clone 下来是 `100644`，跑不了。

#### ⑤ 中文路径的坑，实测复现了

归档目录在 `桌面/新建文件夹/beacon-dmr`，直接构建 → 失败：

### 13.30 收听默认打开 + 发射静音闸 + 记住上一通（第二十九轮，2026-10-27）

这一轮全是「交互上的坑」，而且四条互相咬着：静音逻辑一错，收听开关就跟着乱；
收听一关，回话时又想不起对方是谁。

#### ① ★「右上角按钮自己变成静音」的真凶

用户报：*收听的时候有时候右上角按钮会自动调为静音待收听状态，
当我调为收听状态时又有两个声音对冲。*

根因在 `hdGate()` —— 它本来是半双工闸门（发射或接收时掐掉 HOSE，
免得同一句话从 MMDVM 和 Hoseline 各听一遍）。但它是这么掐的：

```js
// 旧代码（错的）
function hdGate(){
  const busy=TX.txing||Q.rxing;
  if(busy){
    if(state.audioOn){ Q.hd=true; setPlay(false); }   // ← 把用户意图改掉了
  }else if(Q.hd){
    Q.hd=false;
    if(!state.audioOn)setPlay(true);                  // ← 靠反推恢复
  }
}
```

`setPlay(false)` 干的不只是「别出声」，它把 `state.audioOn` 改成 `false`、
按钮文案改成「🔊 听」、还写进 localStorage。于是：

1. 每收到一句话，按钮自己变成「听」—— 用户以为点错了；
2. 恢复靠 `if(!state.audioOn)` 反推。用户一旦自己点了静音，
   下一次收发结束就会**把它强行打开**；
3. 强行打开的那一刻，如果 `Q.hd` 还是 `true`（上一句的收尾事件还没到），
   闸门判定「正在接收 → 该掐」，于是两路声音同时出来 —— 就是用户说的对冲。

**根子是把两件事混成一个变量**：

| 变量 | 语义 | 谁改 |
|---|---|---|
| `state.audioOn` | 用户想不想听 | 只有用户点按钮 |
| `Audio_.muted` | 此刻必须闭嘴 | 收发的状态机 |

修法是拆开：

```js
function txMuteAll(on){
  on=!!on;
  if(Audio_.muted===on)return;   // 幂等：rx/tx 事件很密，别每次都动 gain
  Audio_.setMute(on);
  if(on){
    Audio_.silence();
    if(state.recAudio)stopRecPlay();   // 录音回放也停，别自己和自己对冲
  }
  renderHtSum();
}
function hdGate(){ txMuteAll(TX.txing||Q.rxing); }
```

`Q.hd` 这个字段就此作废（留着定义只是为了不让老代码报错）。

#### ② 静音必须走 gain 斜坡，不能只在 play() 里 return

第一版想省事，在 `Audio_.play()` 开头加 `if(this.muted)return;`。不够 ——
**已经 `start()` 出去的 buffer 不受影响**，发射那一瞬间还能听到上一句的尾巴，
听起来正好就是「自己的声音和自己的声音对冲」。真正的闸要落在增益上：

```js
setMute(on){
  this.muted=!!on;
  if(!this.gain)return;
  const v=on?0:state.volume*state.gain;
  try{ this.gain.gain.setTargetAtTime(v,this.ctx.currentTime,0.008); }
  catch(e){ this.gain.gain.value=v; }
}
```

8ms 淡出：够快（听不出拖尾），又不至于「啪」一声爆音。`play()` 里那句
`if(this.muted)return;` 也保留 —— 静音期间连 buffer 都不建，省 CPU，
也免得恢复时把积压的旧语音一股脑放出来。

#### ③ 收听默认打开，但记住用户手动的静音

`state.audioOn` 默认从 `false` 改成 `true`，冷启动直接守听，想安静自己点右上角。
但**不能无脑打开**：用户手动静音过，下次进来还得是静音，否则等于没记住。
所以 `setPlay()` 里加一行 `store.set('audioOn',!!on)`，boot 时读回来：

```js
setPlay(store.get('audioOn',true)!==false);
```

位置有讲究 —— 必须放在 `renderNetInfo()` 和订阅列表恢复**之后**。
`setPlay(true)` 会顺手 `ensureSpotter()` 去连 HOSE，放太早会连到另一套服务器、
或者带着一张空的订阅表连上去。

浏览器里 `AudioContext` 一开始是 suspended（自动播放策略），但 `Audio_.play()`
每次都会自查 `state.ctx.state` 并 resume，加上 `pointerdown` / `visibilitychange`
兜底和 3 秒一次的 `audioGuard()`，不需要用户先点一下。

#### ④ 记住上一通：`state.lastRx`

用户报：*对方发射完之后我回发射的时候记不住呼号。*

因为 `state.current` 在对方松手那一刻就被清空了（`logCall` 之后 `state.current=null`），
`#nowbar` 立刻回到「暂无通话」。等你要回话时，屏幕上干干净净，谁说得出来刚才跟谁通联。

补一个只活在会话里的记录：

```js
state.lastRx={ srcId:c.srcId, tg:c.tg, call:a.call, name:a.name, at:Date.now() };
```

写点在 `logCall()`（一句结束时），**不持久化** —— 跨会话的「上一通」没有意义，
反而会误导。10 分钟内有效，过期就回到普通占位文案。三处消费它：

| 位置 | 显示 | 交互 |
|---|---|---|
| `#nowbar` 空闲态 | 上一通 BG6XXX · 张三 · 话组 91 · 3 分钟前 | — |
| `#txHint` 就绪态 | 就绪 · 回 **BG6XXX** 张三 `话组 91` · 按住 PTT 说话 | 点呼号/组号 → 发射目标切过去 |
| 折叠摘要条 | 上一通 BG6XXX | 点一下展开操作区 |

呼号做成可点是有原因的：回话时最怕「人在 91，你却发到 46001」。
点一下就切过去，不用翻列表找组号。事件用委托绑在 `#txHint` 上 ——
`txSync()` 会不停重写这行的 `innerHTML`，直接绑子元素会丢。

#### ⑤ 折叠不再把收听状态一起藏起来

用户报：*往下滑看记录的时候，顶部的收听状态就又折叠了看不到了。*

原来折叠是 `.home-op{display:none}`，网络条和发射条一起消失。往下滑看记录时，
屏幕上就只剩列表 —— 有没有人在说话、上一通是谁，全看不到。

折叠的本意是**省屏幕**，不是**把状态藏起来**。所以收掉整块之后补一行 26px 的摘要：

```
🌍 BM   ● 上一通 BG6ABC                                    [91]
```

- 左侧网络（国际/国内）
- 圆点：绿色=正在接收，红色=正在发射，灰色=空闲
- 中间：`BG6XXX 正在说` / `上一通 BG6XXX` / `发射中` / `已静音` / `守听中`

### 13.31 音质：接收去「发抖」+ 发射补抗混叠（第三十轮，2026-10-27）

用户提的是「音质能不能优化一下，包括我发射的收音和其他声音过来的解码」。
两条链路分开看，问题完全不同。

#### ① 接收侧最响的一处劣化：每帧无条件淡入淡出

`handleSpotter()` 和 `handleRwAudio()` 里都抄了同样一段：

```js
const F=Math.min(24,f.length>>2);
for(let i=0;i<F;i++){ const k=i/F; f[i]*=k; f[f.length-1-i]*=k; }
```

注释写的是「消除包边界上的咔哒声」。**方向对，做法错**：它是**每一帧都做**。
μ-law 帧长 160 样本（20 ms），24 个样本占 15%，等于每 20 ms 把幅度压下去再抬起来 ——
一个 50 Hz 的幅度调制。听感就是**声音在「发抖」、发虚**，尤其是拖长的元音。

正确做法是**只在接不上时才淡**：断流恢复、切话组、静音解除。连续的帧本来就连续，
不需要任何处理。所以把这段收进 `Audio_.push()`：

```js
push(f){
  if(!f||!f.length)return;
  const n=f.length;
  if(this.ctx){
    const now=this.ctx.currentTime;
    if(this.nextTime&&(this.nextTime<now+0.02||this.nextTime>now+0.8))this.broken=true;
  }
  if(this.broken){                       // 只有断流后才淡入
    const F=Math.min(24,n>>2);
    for(let i=0;i<F;i++)f[i]*=i/F;
    this.broken=false;
  }
  ...软限幅...
  this.play(f);
}
```

> 这里有个反直觉的坑：`play()` 里本来也会在队列断档时重置 `nextTime`，
> 顺手把 `broken` 也置真 —— 结果**断流后的第二帧又淡了一遍**（第一帧排进来时
> `nextTime` 还是 0，必然命中那个分支）。测试里「第二帧首样本应该保持 0.5」
> 这条断言就是专门盯这个的，第一次跑确实红了。

#### ② 接收侧补一条音色链

DMR 是 8 kHz 窄带，μ-law 解出来直接播有两个毛病：低频隆隆糊成一团，
2.5 kHz 往上掉得快、辅音听不清。所以在 gain 后面串两级：

```js
const hp=this.ctx.createBiquadFilter();
hp.type='highpass'; hp.frequency.value=180; hp.Q.value=0.7;
const pk=this.ctx.createBiquadFilter();
pk.type='peaking'; pk.frequency.value=2600; pk.Q.value=0.9; pk.gain.value=2.5;
this.gain.connect(hp); hp.connect(pk); pk.connect(this.ctx.destination);
```

参数取得很保守。**这是对讲，不是音乐** —— 过度「美化」会让声音失真，
辨识度反而下降。180 Hz 高通不会伤到语音基频：AMBE 编码本身就从 300 Hz 起，
HOSE 推下来的 μ-law 里 300 Hz 以下全是噪声。

#### ③ 软限幅代替硬削波

`state.gain` 默认 2 倍，μ-law 满刻度信号很容易被削平。硬削波产生的高次谐波
在 8 kHz 带宽里**全部叠回话带**，听起来「炸」。改成指数软压缩：

```js
if(x>0.92)f[i]=0.92+0.08*(1-Math.exp(-(x-0.92)/0.08));
```

只在 0.92 以上动手，正常电平一个样本都不改（这条也有断言）。
原生侧 `DmrAudio.writeFrame()` 里同样的硬削也一并换成了软限幅。

#### ④ 发射侧：31 抽头的 FIR 等于没做抗混叠

`DmrTransmitter` 在设备不支持 8 kHz 直采时回退到 48 kHz + 抽取，
抽取前有 FIR 低通 —— 代码是对的，但**抽头数只有 31**：

```
过渡带宽 ≈ 3.1·fs/N = 3.1 × 48000 / 31 ≈ 4800 Hz
```

而 8 kHz 输出只有 3400→4000 Hz 这 **600 Hz** 的余量。31 抽头根本压不住
4 kHz 以上的成分，它们全部折叠回话带 —— 听感就是「金属味、嘶嘶声」，
而且是**发射侧**的，对方听得最清楚，自己在这边完全不知道。

改成 127 抽头，过渡带压到约 1170 Hz。代价是每输出样本 127 次乘加：
8 kHz × 127 ≈ 100 万 MAC/s，对手机可以忽略。

#### ⑤ 发射侧：直流阻断 + 峰值归一化

采集链原来没有任何前端处理：麦克风 PCM 直接进 AMBE 编码器。两个问题：

**直流/低频**。手机在 `MIC` 源下常有几十赫兹的隆隆和直流偏移。
AMBE 的比特预算全在 300–3400 Hz，低频占掉的每一分都是从语音里偷的，
而且编出来是「嗡嗡」的底噪。加一阶高通（120 Hz，状态跨帧保留）：

```java
float y = a * (y1 + x - x1);   // a = 1/(1 + 2π·120/8000) ≈ 0.914
```

**电平**。`MIC` 源的电平各机差异能到 20 dB：同样正常说话，有的设备峰值 3000，
有的 25000。太轻的输入编出来又闷又糊。加一个**峰值归一化**（不是压缩器）：

| 参数 | 值 | 理由 |
|---|---|---|
| 目标峰值 | 20000（≈ -4 dBFS） | 留 4 dB 余量给 AGC 后的瞬态 |
| 最大提升 | 4 倍（+12 dB） | 再高就把底噪也提上来了 |
| 噪声门 | 峰值 < 700 不提升 | 安静时回落到 1 倍，不放大底噪 |
| 攻击 | 0.35/帧（≈60 ms） | 句首立刻起来 |
| 释放 | 0.03/帧（≈650 ms） | 句尾慢慢回落，不「抽气」 |

**只往上提，不往下压** —— 压缩会损失动态，语音变平、辨识度下降。
这是对讲，宁可电平略高，也不要声音发闷。

#### 验证

- `_diag_v18.js` 40 条断言（新增 10 条音质相关），390×844 与 1024×900 **全绿**
- 关键项：`连续帧不再无条件淡变`、`帧中间不再被压`、`软限幅把 2.0 压到 1.0 以内`、
  `正常电平不被软限幅改动`、`高通/提升已串入`
- Java 编译通过（`compileReleaseJavaWithJavac`）

> 编译时踩了一个低级错：把 `private static final int FIR_TAPS` 写在了 `txLoop()`
> **方法体里**。Java 不允许方法内出现 `private`，报的却是「非法表达式开始」，
> 一屏 20 行错误全指向后面几百行。常量必须提到类字段区。

### 13.32 多话组：46001 在说时 91 插进来会打断（第三十一轮，2026-10-27）

用户报：*我的收听如果有多个话组的时候，我在 46001 上面通联，
但是 91 上面来声音了会打断。*

#### 根因：只有一个坑位，而且切换时清空了播放队列

`handleSpotter()` 的 `CALL_START` 分支原来是这样：

```js
const prev=state.current;
if(prev&&prev.tg!==tg)logCall(prev);
state.current={ srcId, tg, alias:'', start:Date.now() };   // ← 直接覆盖
state.active.set(tg,{...});
Audio_.silence();                                          // ← 正在播的全清掉
```

三件事叠在一起：

1. **`state.current` 只有一个**。46001 正在说，91 的 `CALL_START` 一来就把它顶掉；
2. **`Audio_.silence()` 清空播放队列** —— 已经排进去、还没播完的 46001 直接被砍，
   连尾巴都没有；
3. 界面上的呼号跟着跳，看着像「被抢台」。

`audioAllowed()` 只管「这个组有没有订阅」，几个组都订阅了就是全部放行 ——
**没有任何「同一时刻只听一个」的概念**。

#### 修法：照搬扫描器的那套

真实电台扫描多频道靠两个参数，这里用同样的思路：

| 概念 | 作用 | 这里的取值 |
|---|---|---|
| **占用（locked）** | 一个时刻只有一个组能出声 | 正在播的那个 tg |
| **hang time** | 说完不立刻切走，避免两个组来回跳 | 1.8 秒 |

```js
const RXG={ tg:0, at:0, hangMs:1800 };
function rxHold(tg){          // 是否被别的组占着
  tg=Number(tg)||0;
  if(!RXG.tg||RXG.tg===tg)return 0;
  return (Date.now()-RXG.at)<RXG.hangMs?RXG.tg:0;
}
function rxTake(tg){ RXG.tg=Number(tg)||0; RXG.at=Date.now(); }  // 每帧刷新
```

- `CALL_START` 时先问 `rxHold(tg)`：被占着就**不切 current、不 silence**，
  只往 `active` 里记一笔（列表里能看到它在呼叫），然后 return；
- `CALL_AUDIO` 每帧调 `rxTake()` 刷新时间戳 —— **还在说就一直占着**，
  不会因为中间隔了半秒就被人抢走；
- `CALL_END` 时调 `rxRelease()`：如果 `active` 里还有别的组在等，立刻让位，
  不用干等 1.8 秒。

另外三个地方必须主动释放占用，否则「点了没反应」：

| 动作 | 为什么 |
|---|---|
| 点话组（`txSetTarget`） | 用户主动点了 = 想听它，不该再被别的组压 1.8 秒 |
| 切独听（`toggleSolo`） | 收听范围变了，旧占用作废 |
| 切网络 / 断流（`spotterClose` / `rwClose`） | 指向的是另一套话组号 |

#### 局限：HOSE 的音频帧里没有话组号

这一点必须写清楚，否则以后会有人以为「已经彻底隔离了」。

```
HOSE  CALL_START [type, _, srcId, tg]      ← 有 tg
HOSE  CALL_AUDIO [type, Uint8Array]        ← 没有 tg
```

音频帧不带组号，归属只能靠 `state.current` 推断。所以「让路」能做到的是
**不切换、不清队列、不打断正在听的那一句**，做不到「把插进来的那句话单独丢掉」。
真要彻底隔离，只能用「独听」（一次只订阅一个组）。

**国内 China DMR 不一样**：那边是多流，每帧前 4 字节就是 `stream_id`，
能映射回话组。所以 `handleRwAudio()` 里是真隔离 ——

```js
if(rxHold(tg))return;   // 别的组在说，整帧丢掉，不会串进来
rxTake(tg);
```

#### 交互：让路不能悄无声息

不提示的话，用户会以为「91 根本没收到」，其实是收到了但没播。所以在让路时给一次
toast（同一组 20 秒内只提示一次，别把界面刷爆）：

> 话组 91 有呼叫 · 正在听 46001（点它可切过去）

「点它」是真的能点：列表里点任意一行话组就会 `txSetTarget()`，顺带 `rxReset()`
把占用让出去，下一帧音频就进来了。

#### 验证

`_diag_v18.js` 第 7 节新增 9 条断言，390×844 与 1024×900 均 **49 通过 / 0 失败**：

- `46001 开口后占住坑位`
- `91 插进来不打断（current 仍是 46001）`
- `91 仍记进 active（列表里能看到）`
- `rxHold(91) 返回占用的 46001`
- `挂起窗口过后 91 可以接管`
- `CALL_END 后坑位让给还在等的组`
- `点话组后立刻释放占用`
- `切独听后释放占用`

`smoke_cn.js` 166 通过 / 0 失败。
