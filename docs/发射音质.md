# 发射音质：从「糊」到能听清

这份文档记录 v2.0 → v2.1 对发射音质的排查过程。**结论来自代码和仿真，不来自主观描述**；
每一处改动都对应一个可量化的失效。

## 一、先确定「听到的到底是哪一版」

拿到一段别人抄收的录音（5.76 秒，手机对着电台喇叭录的）时，第一件事不是分析频谱，
而是确定它是哪个版本发出去的 —— 否则改错地方。

判据是低频：v2.0 把高通从「一阶 120 Hz」换成了「二阶 280 Hz」。
如果是 v2.0，60–100 Hz 应该比中频低 40 dB 量级；v1.9 那个一阶高通做不到（只有 −12 dB）。

实测：60–100 Hz 相对峰值 −40.2 dB，且 `clipSamples = 0`、峰值 −0.6 dBFS
（正是 v2.0 软限幅的效果）。**判定为 v2.0。**

这意味着：**低频已经不是问题了**，用户的「糊」不是低频造成的。

## 二、手机录音能说明什么，不能说明什么

这段录音是「手机麦克风 → 电台喇叭」的声学录音，中间隔着：手机麦克风的频响、
手机的 AI 降噪、房间声学、电台喇叭的频响。它**不能**用来判断发射链的频响。

一个例子：录音里 3200–4000 Hz 在「语音帧」和「底噪帧」里都是 0 dB。
这不可能是我们发出去的 —— AMBE 带宽 3.2 kHz 封顶。说明这一档整个是房间噪声，
归一化基准被它带跑了，上面所有 dB 数字都偏了。**拿它当 EQ 依据是过度解读。**

它**能**说明的是：

| 项目 | 实测 | 结论 |
|---|---|---|
| 满刻度样本数 | 0 | 没有削波 |
| 峰值 | −0.6 dBFS | 电平充足 |
| 语音时长 | 4.7 / 5.76 s | 连续，没有断字 |
| 断点（≥300 ms） | 1 | 正常换气 |

这三条都不是「不清晰」的原因。于是转向代码。

## 三、四个真正的 bug

### 1. AGC 状态跨发射残留（影响最大）

`agcGain` / `rmsAvg` / `agcFrames` 是 `DmrTransmitter` 的实例字段，而实例随引擎活着。
`start()` 里从来没有重置它们。

后果：`agcFrames` 只增不减，`agcFrames < AGC_FAST_FRAMES` 那段「开头 160 ms 快速收敛」
**只有开机后第一次 PTT 才会走到**。之后每次发射都从上一通残留的增益起步，
按 1 秒的慢速收敛。

仿真（上一通大声、这一通轻声）：

| | 首帧增益 | 与理想值的偏差 |
|---|---|---|
| 不重置（v2.0） | 0.72× | **−20.5 dB** |
| 重置（v2.1） | 7.64× | 0.0 dB |

而「呼号」恰好就在这一秒里。

修法：`start()` 里清零 AGC 状态；并且**首帧直接赋值到 `want`，不爬**
（发射刚开始、还没有输出，直接赋值不会有爆音风险）。只有这一帧确实有声音
（过了静音门限）才快照，否则一按 PTT 就先把增益顶到 8× 等着，开口第一下必炸。

### 2. AGC 的 slew 方向写反了

```java
float k = (want > agcGain) ? 0.30f : 0.06f;   // v2.0
```

`want > agcGain` 意味着**信号变轻了、需要提增益**，走 0.30（快）；
信号变响、需要压增益走 0.06（慢）。**正好和压缩器该有的方向相反。**

仿真（轻声 1 秒后突然大声 1 秒）：

| 大声段位置 | v2.0 过冲 | v2.1 过冲 |
|---|---|---|
| 100 ms | +10.3 dB | +11.7 dB |
| 200 ms | +7.7 dB | **+2.3 dB** |
| 500 ms | +3.5 dB | −1.8 dB |

100 ms 那一点没有改善（那是起音本身，没有前瞻就无法预知），但 200 ms 之后
差 5.4 dB。过冲会被软限幅压平，AMBE 编出来就是糊的。

修法：`k = (want < agcGain) ? 0.35f : 0.08f` —— 压快（≈50 ms）、提慢（≈250 ms）。

### 3. 电平检测器上升/下降共用时间常数

`rmsAvg` 用同一个 `0.02` 双向平滑。说一句话，中间的停顿让检测器按 1 秒的速率往下掉，
下一个词回来时又要 1 秒才追上。

修法：上升用 `0.25`（≈80 ms）、下降仍用 `0.02`。检测器记住的是**这段说话的峰值电平**，
短停顿不会把它带下去。这是所有电台电平器的标准做法。

### 4. 声码器前没有降噪

这是「不干净」的直接来源。链条是这样坏的：

轻声说话 → AGC 判出 7.4× → 增益应用到整段信号，**包括词与词之间的麦克风本底噪声**
→ 噪声底 −65 dBFS 抬到 −48 dBFS 送进声码器。AMBE+2 只有 2.45 kbps，
它不区分「这是噪声」，照样分配比特去编码。

修法：在 **AGC 之后**加一级噪声门（下行扩展器）。位置很关键 —— 放前面的话
AGC 会把它压掉的噪声原样再提回来，等于白做。

仿真（底噪 −62 dBFS，说话-停顿-说话-长停顿-说话）：

| | 说话段 | 长停顿 | 语音/底噪 |
|---|---|---|---|
| 无门（v2.0） | −16.8 dBFS | −48.0 dBFS | 31.2 dB |
| 有门（v2.1） | **−16.8 dBFS** | −55.0 dBFS | **38.2 dB** |

**说话段电平一模一样（4738 → 4738）**，一个字节都没吃掉；底噪压了 7 dB。

三个设计点：保持窗 320 ms（没有它词间低谷会让门反复开合，听感是「吃字」）；
只压 18 dB 不全静音（全静音像断线）；门限用**处理前**的 RMS 判断
（那是增益无关的量，AGC 怎么变都不影响「这一帧是人声还是噪声」）。

## 四、两处参数调整

### presence 从 2.6 kHz 下移到 2 kHz

v2.0 打在 2600 Hz / +2 dB / Q 0.8。Q=0.8 时带宽 = f0/Q = 3250 Hz，
实际是从 1 kHz 到 4.2 kHz 一个很宽的缓抬 —— 重心偏高。2.6 kHz 以上主要是
s/sh 的齿音，AMBE+2 在这一段最容易把它编成刺耳的噪声；而真正决定「字咬得清不清」
的是 **1–2.5 kHz**（第二共振峰 F2 的过渡段）。

| | 可懂度核心 900–2000 Hz | 齿音区 2400–3200 Hz | 核心/齿音 |
|---|---|---|---|
| v2.0 | +0.63 dB | +1.54 dB | −0.91 dB |
| v2.1 | **+1.87 dB** | +1.26 dB | **+0.62 dB** |

### AGC 目标电平从 −18.3 提到 −16 dBFS

依据来自声码器自检代码：`vocoder_jni.cpp` 的 `makeSpeechLike()` 把测试信号
归一化到**峰值 24000**，注释写的是「留 3 dB 余量，避免定点分析前端溢出」——
那是这个 IMBE 定点前端验证过的工作点。

按语音 12 dB 峰值因数反推，RMS 4000 对应峰值约 15900，比工作点低 4 dB：
定点前端的有效位没用满，量化噪声占比偏高，听感就是「闷」。5200 对应峰值约 20800
（−3.9 dBFS），仍在软限幅拐点（−0.7 dBFS）之下。

### 抗混叠 FIR 的窗从 Hann 换成 Hamming

两者主瓣宽度差不多，但阻带差 12 dB（−31 → −43 dB）。这条通道的任务是压住
4 kHz 以上别折叠回话带，手机 MIC 在 4–8 kHz 的能量一点不少。
折叠回来的混叠落在 1–4 kHz 就是一层持续的「沙沙」，而这段正是可懂度核心区。

## 五、这个软件声码器的天花板

必须说清楚：`third_party/droidstar-vocoder-plugin` 是**纯软件** AMBE+2，
IMBE 定点分析前端 + AMBE 2450×1150 量化。自检代码里就有一句：
「或这个软件声码器的合成质量本身就很差」。

真实 DMR 手台用的是 DVSI 的硬件声码器。2.45 kbps 的参数化编码，加上软件实现的
合成质量，**不可能达到模拟 FM 手台的听感** —— 模拟 FM 传的是连续波形，
带宽约 3 kHz，没有参数量化这一步。

v2.1 能保证的是：电平一致（不再「一开口音量是错的」）、不削波、不抽气、
底噪压低 7 dB、能量重心移到可懂度核心区。**这是这个编码方式的上限附近。**

如果还想再进一步，剩下的只有一条路：换声码器实现。那不是调参能解决的。

## 六、关于「860 比 4602 好听」

同一个手机、同一条发射链，发到不同主站听到的效果不同 —— **说明差异不在编码器**。
我们发出的 AMBE 码字是一样的，两个主站都只是转发这些码字。

差异只可能来自下游：主站之间的转码桥接、收听方的热点/手台、以及收听的人。
**这个方向 App 改不了。**

反过来说，这件事有个正面意义：如果 860 听起来可以接受，说明手机→主站这一段
没有丢包/错帧问题，那么剩下的差距就确实在发射前端 —— 正是 v2.1 改的那几处。

## 七、断续（v2.2）

v2.1 发出去之后对方抄收反馈「话音断续」。这一节的排查过程比结论更重要 ——
**因为前两个假设都被我自己推翻了。**

### 断续只可能来自三处

1. **丢包** —— 网络或主站侧，App 改不了。
2. **帧时间轴错乱** —— 每 20 ms 必须交出一帧。漏一帧、补一帧、慢一帧，
   对方听到的就是一个 20 ms 的断口或跳变。攒够几次就是「断续」。
3. **增益调制** —— AGC 或噪声门在说话过程中反复压/放，听起来也像断续。

### 假设一：噪声门切掉了词头 —— 推翻

怀疑很自然：v2.0 的噪声门保持窗只有 320 ms，而正常说话的词间停顿
300~500 ms 很常见。保持窗一过门就关，下一个词的起音就被压着。

于是写了个仿真 `tests/tx_gate_chop.py`，喂不同长度的停顿，量下一个词的起音被压多少 dB。
结果：**最多只压 2.8 dB**。

2.8 dB 是听得出来「有点闷」，但**绝不足以造成断续**。假设不成立。

参数还是改了（保持窗 320 → 600 ms、开门改成硬开、最大衰减 14 dB），
因为方向是对的、代价为零。但**它不是断续的原因**。

### 假设二：声码器编解码共用一把锁 —— 推翻

`vocoder_jni.cpp` 里编码和解码共用一把 `g_lock`。文件头注释第 4 条明明写着
「编码与解码各持一个实例，分开后互不干扰」—— 一把全局锁让这个设计白做了。

看起来很像元凶：发射线程是硬实时，等锁就等于漏帧。

但翻 `DmrEngine.java`：

```java
if (rxOn && payload != null && vocoderReady && !transmitter.isTransmitting()) {
```

**发射时接收解码是跳过的。** 所以发射期间根本不存在锁竞争。

锁还是拆成了 `g_encLock` / `g_decLock`（设计意图本来如此，且 `nativeRelease`
要按 `g_lock → g_encLock → g_decLock` 的顺序三把都拿住），但**它也不是断续的原因**。

### 真正的候选一：采集缓冲按 8 kHz 算，48 kHz 下小 6 倍

```java
// v2.1
int bufBytes = Math.max(minBuf, FRAME_SAMPLES * 2 * decim * 32);
```

注释写的是「32 帧 = 640 ms」，但 `FRAME_SAMPLES * 2` 只是 **8 kHz 直采**时的一帧字节数。
走 48 kHz 抽取时一帧是 `160 × 6 = 960` 个采样，同一个算式只给出 **107 ms** ——
比设计意图小 6 倍。

107 ms 的采集缓冲意味着：只要发射线程被调度器拖一下（GC、系统抢占、别的 App），
缓冲立刻见底，`read()` 拿不到够一帧的数据，这一帧就没了。

修法：

```java
final int decim = needResample ? (rate / TARGET_RATE) : 1;
int bufBytes = Math.max(minBuf, FRAME_SAMPLES * 2 * decim * 32);
```

### 真正的候选二：发射线程优先级不够

`txLoop` 是硬实时循环，原来没设优先级。Android 上普通线程被抢占几十毫秒很正常。
现在进循环第一件事：

```java
android.os.Process.setThreadPriority(android.os.Process.THREAD_PRIORITY_URGENT_AUDIO);
```

### 顺手修掉的硬 bug：编码失败 `continue`

```java
if (Vocoder.nativeEncode(pcm, ambe) != Vocoder.CODEC_BYTES) {
    continue;   // ← v2.1
}
```

`continue` 让这一帧「消失」，但 `bundleFill` 不前进 —— 下一个帧直接顶上来，
于是这个 60 ms 的包里装的是「第 n 帧 + 第 n+2 帧 + 第 n+3 帧」，
**时间轴被压缩了 20 ms**。对方听到的就是一次跳变。

改成沿用上一帧的码字：

```java
} else {
    encodeFail = 0;
}
```

### 怎么在真机上判定到底是哪一种

新增了一条健康度日志，每 5 秒报一次：

```
发射健康：250 帧，处理 平均 3.2 ms / 峰值 11 ms（预算 20 ms）
```

- **峰值 < 20 ms** → CPU 跟得上，断续在网络/主站侧，App 改不了。
- **峰值 ≥ 20 ms（日志会标 ⚠）** → 发射线程来不及，会积压，问题在算法或线程调度。
- 平均低但峰值高 → 典型的被抢占，优先级修复应该有效。
- 平均就接近 20 ms → 算法本身太重，得砍 FIR 阶数或降低采样率。

这条日志是判断「到底是 CPU 跟不上还是算法问题」的直接证据，
比继续猜有用得多。

## 八、断续（v2.3）：节拍

v2.2 装上之后拿到一份完整运行日志。**日志里有一行直接推翻了 v2.2 的主假设。**

### 日志推翻的：这台机器根本不做抽取

```
[14:26:17] 开始发射 → 46001（8000 Hz）
```

`8000 Hz` 说明 `AudioRecord.getMinBufferSize(8000, ...)` 返回了正值，
走的是 **8 kHz 直采**，`decim = 1`。而 v2.2 改的是

```java
int bufBytes = Math.max(minBuf, FRAME_SAMPLES * 2 * decim * 32);
```

`decim = 1` 时新旧算式完全一样。**那个「缓冲小 6 倍」的修复对这台机器一点作用都没有。**
（它仍然是对的 —— 48 kHz 的机器上确实是 107 ms —— 只是不是这位用户的病因。）

### 日志还说明：健康度报告根本不会触发

```
[14:26:17] 开始发射    [14:26:18] 停止发射   （1 秒）
[14:26:19] 开始发射    [14:26:22] 停止发射   （3 秒）
[14:27:02] 开始发射    [14:27:07] 停止发射   （5 秒）
```

v2.2 的报告间隔是 5 秒，而实际发射只有 1~5 秒 —— **大部分时候等不到报告点**。
这就是日志里一条「发射健康」都没有的原因。诊断本身设计错了。

改成 2 秒一报，并且**松开 PTT 时必定打一份完整小结**。

### 新发现：发包节奏从来没有节拍控制

一个 DMRD 包 = 27 字节 = 3 个 AMBE 帧 = **60 ms 音频**。空口上必须严格每 60 ms 一个，
这是 MMDVMHost 的做法（定时器驱动）。

而原来的实现是「采集驱动」：

```java
bundleFill += Vocoder.CODEC_BYTES;
if (bundleFill >= DmrTx.AMBE_BUNDLE) { bundleFill = 0; send(); }
```

每读满一帧（20 ms）编一次码，攒满 3 帧就发。这等于假设
「`AudioRecord.read()` 一定每 20 ms 返回一次」。

问题在于 AudioRecord 的缓冲**可以积压**。一旦积压（刚 startRecording、
GC 停顿、系统抢占之后都会），`read()` 会连续多次立即返回 —— 于是几个包在
1~2 ms 内全发出去，然后静默。空口上这就是「突发 + 静默」，对方听到的就是断续，
而网络统计里一个包都没丢。

`tests/tx_pacing_sim.py` 把这个量化了。场景：发射开始时缓冲里已有 32 帧（640 ms）。

| | 最小包间隔 | 最大包间隔 | <50 ms 的包 |
|---|---|---|---|
| 原实现（采集驱动） | **7.5 ms** | **587.5 ms** | 9 / 48 |
| v2.3（60 ms 节拍） | 60.0 ms | 115.0 ms | 0 / 48 |

**最小 7.5 ms 意味着 60 ms 的音频被塞进 7.5 ms 发完；最大 587.5 ms 意味着
有近 0.6 秒一个包都没发。** 而这台机器的发射本身只有 1~5 秒 ——
开头这 0.6 秒的静默正好盖住呼号。

修法是绝对时间轴：

```java
final long PKT_PERIOD_NS = 60_000_000L;
long early = nextPktAt - now;      // >0 = 比节拍早
if (early > 0) { Thread.sleep(...); nextPktAt += PKT_PERIOD_NS; }
else if (early < -2 * PKT_PERIOD_NS) { nextPktAt = now + PKT_PERIOD_NS; }
else { nextPktAt += PKT_PERIOD_NS; }
```

注意「早到就等、晚到就重新对齐」这两个方向都要有：
只等不对齐，一次长时间的停顿会让 `nextPktAt` 永远落后，之后每个包都迟到。

代价是**延迟**：积压的音频不再靠突发发完，而是按节拍慢慢发，于是延迟会一直存在。
这是有意的取舍 —— 对 DMR 来说 200 ms 延迟无害（收听侧本来就有抖动缓冲），
而 0.6 秒的空口静默是致命的。

### 顺手修掉的两个「会死循环」的坑

```java
if (got < readPerFrame) continue;      // ← v2.2
```

`got` 是内层循环的局部变量，`continue` 之后从 0 重来，**已经读到的那几个采样被扔掉**。
时间轴就少那几毫秒。改成 `rawFill` 累加器，只在完整消费一帧之后才清零。

还有「连续 read 返回 0」的保护计数 `spin` 声明在外层循环里，
**每次外层迭代都会清零** —— 那个「连续 200 次就报错」的保护等于永远不成立。
移到外层循环之外。

另外 `read()` 返回 `ERROR_DEAD_OBJECT`（-6）时原来不停机，
会掉进 `continue` 变成**发射线程空转、一个包都不发**。改成任何负值都停机。

### v2.3 的诊断能做到什么

每次松开 PTT 都会打一份小结：

```
发射小结：4.8 秒 · 240 帧 · 80 包
  音频时钟：采集 4800 ms vs 实时 4812 ms（差 -12 ms，0.2%）
  读      ：平均 20 / 峰值 47 ms（正常 20）· 短读 0 次
  处理    ：平均 2.9 / 峰值 11 ms（预算 20）
  发包    ：间隔峰值 78 ms（应为 60）· 提前 2 / 迟到 0
  编码    ：失败 0 帧
```

怎么读：

- **音频时钟差** 是最硬的指标。采集和实时必须一致；差超过 3% 就是麦克风侧在丢样本
  （AudioRecord 缓冲被覆盖时不报错，只能这样反推）。
- **读 平均** 应该接近 20 ms。远小于 20 = 缓冲有积压；远大于 20 = 线程被抢占。
- **处理 峰值** 超 20 ms = CPU 跟不上，跟算法无关。
- **发包 间隔峰值** 应接近 60。远超 60 = 有空口静默。
- **短读** 大量出现 = 麦克风 HAL 有问题。

如果这份小结全部正常，而对方仍报断续，那问题就**确定不在 App 的发射链**，
只可能在网络丢包或主站侧 —— 那时候再改代码是浪费时间。

## 九、v2.3 / v2.4 发出去的是静音（v2.4.1 修复）

这一节是给自己看的反面教材。

### 事故

v2.3 重写 `txLoop`（加发包节拍）时，漏掉了一行：

```java
System.arraycopy(ambe, 0, bundle, bundleFill, Vocoder.CODEC_BYTES);
```

后果不是报错、不是崩溃，而是**发出去的全是静音**：

- `bundle` 是 `byte[27]`，Java 的初始值**全是 0**；
- 少一次拷贝，每个 DMRD 包里装的就是三帧全零码字；
- PTT 照按、电平条照跳、包照发、主站照转、发射小结干干净净；
- **对方一个字都听不到。**

v2.3 和 v2.4 两个版本就这样发出去了。用户的原话是
「能发射出去但始终没有任何声音传出去」——描述得非常准确。

### 为什么没被发现

因为**这条链上没有任何一个指标会变**：

| 指标 | 静音时的值 | 正常时的值 |
|---|---|---|
| PTT 状态 | 发射中 | 发射中 |
| 麦克风电平条 | 跟着说话跳 | 跟着说话跳 |
| 发包数量 | 正常 | 正常 |
| 主站回应 | 正常 | 正常 |
| 音频时钟差 | 0% | 0% |
| 编码失败数 | 0 | 0 |

`frameRms`、`agc`、`noiseGate`、`nativeEncode` 全都正常工作 ——
**数据在 `ambe[]` 里是对的，只是没被搬进 `bundle[]`**。
所有我上一轮加的诊断都测在「编码之前」，恰好绕开了这一行。

### 两个补救

**1. 源码不变量检查：`tests/check_tx_bundle.py`**

读 `DmrTransmitter.java`，验证七组结构关系：

1. `ambe → bundle` 的 `arraycopy` 存在，且在 `bundleFill +=` 之前、
   在 `nativeVoice(bundle, …)` 之前；
2. `bundleFill` 发完清零；
3. 编码失败分支里没有 `continue`；
4. 前端处理链顺序为 高通 → presence → 量电平 → AGC → 噪声门；
5. 60 ms 节拍常量与两个方向的对齐都在；
6. 采集用 `rawFill` 累加、连续 0 读的保护计数在循环外；
7. 用户麦克风增益在 AGC 与噪声门**之后**，发射电平在增益**之后**量（v2.4.2 加）。

拿 v2.3 的源码喂给它，前三项立刻失败 —— 这个测试**是被验证过能抓到那个 bug 的**，
不是写完就算。

**2. 运行时探针**

源码检查只能守住这一个文件。真机上还需要一个不依赖测试的手段：

```java
if (frameRms > ZERO_CODE_RMS && isAllZero(ambe)) {
    zeroCode++;
    if (zeroCode == ZERO_CODE_FRAMES) {   // 25 帧 = 0.5 秒
        log("⚠ 连续 25 帧码字全为 0，但麦克风有信号……对方会听到完全的静音");
    }
} else {
    zeroCode = 0;
}
```

判据是「麦克风有信号（RMS > 800 ≈ −32 dBFS）+ 码字全 0」。
AMBE 的静音帧**不是全零**（自检里静音码字是 `46 44 60 20 07 F0 C4 08 01`），
所以这个组合不可能正常出现。

### 教训

**「重构一个循环」和「重构一个函数」不是一回事。**
函数有签名兜着，少传一个参数编译就过不了；
循环里的缓冲区搬运没有任何类型约束 —— `bundle` 少写一次照样编译、照样运行、
照样「看起来正常」。凡是「往缓冲区里搬数据」的代码，重构后必须逐个缓冲区核对
「谁写、写几次、写到哪」。

**诊断要测在链路的末端，不能只测前端。**
上一轮加的健康度全在「编码之前」，所以编码之后的静音它一个字都报不出来。
现在补的探针测的是**真正要发出去的那 27 个字节**。

## 十、麦克风增益（v2.4.2）

用户的要求是「加一个麦克风增益调节」。听起来是加法，实际难点只有一个：
**放在链的哪一节**。

### 为什么不能放在最前面

链里已经有 AGC：

```
高通 → presence → 量电平 → AGC（目标 −16 dBFS）→ 噪声门
```

AGC 的职责就是把输入音量拉到一个**固定**的目标值。它不知道也不在乎你在它前面
乘了什么 —— 你在前面放大 6 dB，它就在后面把增益降 6 dB，输出电平回到 −16 dBFS，
一个 bit 都没变。

用户拖动滑块，声音毫无变化。他会得出两个结论之一：「这功能是假的」，
或者「我手机麦克风坏了」。**一个能拖但不起作用的控件，比没有这个控件更糟。**

### 放在哪，以及为什么

```java
highPass(pcm);
presence(pcm);
final float frameRms = rmsOf(pcm);
agc(pcm, frameRms);
noiseGate(pcm, frameRms);   /* ★ 必须在 AGC 之后 */
applyMicGain(pcm);          /* ★ 用户增益在 AGC 之后 */
```

放在 `noiseGate` 之后有两个好处：

1. AGC 已经收敛，增益是**乘在稳定信号上**的，抬多少就是多少；
2. 噪声门先执行，抬增益不会把已经被门压掉的底噪重新提回来。

### 顺带一个容易漏的点：读数也要挪

发射电平原来是在 AGC 之后、增益之前量的。加了增益之后如果不改，
用户拖滑块时**声音变了但读数不动** —— 和「调了没反应」是同一种误导。
所以电平改成在 `applyMicGain` 之后量：

```java
if (listener != null) {
    final float outRms = rmsOf(pcm);
    listener.onLevel(levelOfRms(outRms), dbOfRms(outRms));
}
```

这样拖滑块时读数跟着动，用户能自己看出「+9 dB 之后只剩 3 dB 余量了」。

### 软限幅，不是硬削

+12 dB 意味着采样值乘以 4。正常说话峰值 ~12000，乘完 48000 —— 早就越过 32767。
直接 `(short)` 转换会截断成方波，谐波一片，AMBE 编出来是刺耳的破音。

```java
private static short softLimit(float v) {
    final float abs = v < 0 ? -v : v;
    if (abs <= SOFT_KNEE) return (short) v;          // 26000 以下原样
    final float room  = 32767f - SOFT_KNEE;
    final float over  = abs - SOFT_KNEE;
    final float shaped = SOFT_KNEE + room * (over / (over + room));
    return (short) (v < 0 ? -shaped : shaped);       // 永远 < 32767
}
```

越过膝点之后按 `room·over/(over+room)` 逼近满量程：**单调、连续、永不触顶**。
代价是过头之后声音会「变平」—— 峰值被压在一起，起伏没了，对方听上去是
「一直很响、没有语调」。所以界面上直接写明安全区间是 **−6 ~ +6 dB**，
而不是把范围开到 ±12 却假装它随便用。

### 增益的作用范围

−12 ~ +12 dB，步进 1 dB，默认 0。**默认必须是 0** —— 这是「用户口味」，
不是「系统需要的修正」。任何非零的默认值都会让没调过的人听起来和别人不一样。

值存在 `localStorage`，进页面回填；原生侧每次冷启动从 0 开始，
所以页面启动时会把存储值下发一次。反过来如果存储被清过而原生还留着旧值，
`dmrStatus()` 里的 `micGain` 字段会在第一次轮询时把界面纠正回来 ——
「显示和实际不一致」是这类设置最不该有的状态。

### 测试

`tests/smoke_ui.js` 第 13 节 13 项：范围、正负号显示、非 0 点亮、越界夹值、
写存储、`level` 事件带 dB、松手后变暗但保留读数。
音频本身测不到 —— **增益到底有没有效果只能靠耳朵**，测试只能保证
「值真的送出去了、夹住了、读数跟手」。

## 十一、增益拉到底还是炸（v2.4.3）

v2.4.2 加了麦克风增益之后，用户的反馈是：

> 增益调到 −12 声音发炸好了一点但是还是不够

「好了一点」说明这个旋钮确实起作用了；「还是不够」说明它**起错了作用**。

### 病因：限幅在增益之前

v2.4.2 的链序是：

```
AGC（内含软限幅）→ 噪声门 → 用户增益
```

软限幅写在 `agc()` 里，用户增益在它**后面**。于是调小增益的效果是：

> 把一个**已经失真**的信号整体乘小。

谐波一个没少，只是音量小了。对方听到的是「小一点的炸」——
正好就是用户的描述。

更糟的是这条链里有两个限幅实现（`agc()` 内联的膝点 + `softLimit()`），
各自一套膝点常数（30146 和 26000），互相不知道对方在做什么。

### 修法：并进同一个乘数

```java
final float g = agcGain * micGain;   // 用户增益并进 AGC 的输出乘数
...
float x = pcm[i] * g;
if (a > KNEE) { ... 软限幅 ... }     // 限幅在这之后
```

两个约束同时满足：

| 约束 | 为什么 |
|---|---|
| 在 AGC **算完增益之后** | 放在前面会被 AGC 原样抵消 |
| 在软限幅**之前** | 放在后面只能把已经失真的声音调小 |

效果：调小增益 → 送进限幅的信号本来就小 → 限幅根本不介入 →
**失真跟着一起消失**，而不只是变小声。

同时删掉重复的 `softLimit()`，只留 `agc()` 里那一个膝点。

### 顺带修掉的两个问题

**1. 范围 −12 不够 → 扩到 −24**

用户已经拉到最左还说炸。既然滑块是唯一的用户侧手段，下限就该给足。
0 dB 仍是不变的默认值。

**2. 发射电平读数在停顿帧上掉到 −55 dB**

v2.4.2 的读数取的是**当前帧**的 RMS。说话总有停顿，一停顿就掉到
−54.9 dBFS（用户的截图里就是这个数），完全没法用来判断该往哪边调。

改成**本次发射的峰值**：每帧取 max，按下 PTT 时清零。
这样松手时看到的是「这一句最响到过多少」，才是调增益需要的那个数。

### 三个探针：把「炸」分到具体一级

「对方说发炸」这个描述，至少对应两种完全不同的原因，而处置方式相反：

| 探针 | 位置 | 高了说明 |
|---|---|---|
| `inClip` | `AudioRecord.read()` 一出来、任何处理之前 | **手机 MIC 自己过载**。波形顶端已经削平，后面任何增益、限幅、降噪都救不回来 —— 只能离话筒远一点 |
| `limHits` | 软限幅级 | **我们后级太激进**。调小增益有效，而且是真有效 |
| `outPeakDb` | 送进声码器之前 | 整体电平；低于 −30 dBFS 说明离得远或说话轻 |

以前这三种情况的日志**长得一模一样**，所以只能靠猜。现在松手后的小结直接写：

```
  电平    ：送出声码器最高 -14.2 dBFS（短时 RMS，−16 附近正常）
  削波    ：采集 0.00%（前级）· 限幅 3.41%（后级）
  判断    ：⚠ 软限幅在持续介入 —— 把麦克风增益往左调，这次会真的少失真而不只是变小声
```

判据用**比例**而不是绝对值：前级削波超过 0.2% 就已经是可闻的失真了，
因为削波只在波峰上发生，而波峰占的采样比例本来就很小。

### 教训

**「加一个旋钮」不是加一个乘数，是要重新想一遍它该插在哪两级之间。**
v2.4.2 我只想了「不能被 AGC 抵消」，没想到「不能落在限幅之后」——
而后者恰好是用户唯一能感知到的那个作用。

一个旋钮如果只能调音量、调不了音质，那它和手机的音量键没有区别，
用户就会一直拉到尽头然后说「还是不行」。
