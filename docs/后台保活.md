# 切后台就断链：为什么 WakeLock 不够

## 一、现象

连上主站、守听正常，切到别的 App（或熄屏几分钟）再回来，链路已经断了。
重连时还可能被主站判成「同 ID 重复登录」回 `MSTNAK`。

## 二、根因：cached process 会被冻结

Android 8 之后，应用退到后台就是一个 **cached process**：

- 进程可以被**冻结**（freezer），线程不再被调度 —— 不是「变慢」，是**完全停住**；
- Doze / App Standby 会限制它的网络；
- 内存吃紧时它是第一批被杀的。

而 DMR 主站会话是「UDP 链路 + 每 5 秒一次 `RPTPING` 心跳」。
进程被冻结十几秒，主站就判超时、把会话摘掉。

### 关键点：Partial WakeLock 锁的是 CPU，不是进程优先级

早先的实现只持了 `PARTIAL_WAKE_LOCK`，所以：

- **熄屏能听** —— CPU 不休眠，WebAudio 的调度线程照常跑；
- **切后台会断** —— 进程仍是 cached，照样被冻结。

这两件事是**正交**的，必须一起做：

| 手段 | 解决什么 | 不解决什么 |
|---|---|---|
| `PARTIAL_WAKE_LOCK` | CPU 不休眠 | 进程被冻结 / 被回收 |
| `startForeground()` | 进程升到前台优先级，不被冻结/回收 | 熄屏后 CPU 休眠 |
| `WifiLock(HIGH_PERF)` | 熄屏后 WiFi 射频不掉速 | 进程优先级 |

## 三、为什么选 `mediaPlayback` 而不是 `dataSync`

Android 14 对前台服务按类型加限制：

- `dataSync` —— **每天累计 6 小时**上限，超了系统直接掐掉。守听一整天的场景必撞。
- `mediaPlayback` —— 没有时长上限，且这个 App 确实在播放接收到的语音。

所以清单里声明 `android:foregroundServiceType="mediaPlayback"`，
并申请 `FOREGROUND_SERVICE_MEDIA_PLAYBACK`（Android 14 起每种类型要单独申请）。

## 四、几个容易踩的点

**`stopWithTask="true"` 必须加。**
引擎（`DmrEngine`）活在 `MainActivity` 里。从最近任务划掉 App 时 Activity 销毁、
引擎跟着死，如果服务还活着，就变成「挂一条通知、持着锁、什么都不干」的空壳 ——
既耗电又误导。

**只在目标状态变化时才动服务。**
`onDmrEvent` 每个事件都调一次同步函数，如果每次都 `startForegroundService`，
通知会不停闪。用一个 `keepAliveOn` 记住当前状态，变了才动。

**Android 13+ 的 `POST_NOTIFICATIONS` 没授权也不影响运行。**
服务照常拿到前台优先级，只是那条通知不显示。所以不需要为它阻塞流程。

**Android 12+ 从后台启动前台服务会抛 `ForegroundServiceStartNotAllowedException`。**
本 App 都从前台 Activity 启动，正常不会触发；但代码里仍做了 try/catch，
退化成「普通服务 + 持锁」，比崩掉好。

## 五、改完之后仍可能断的情况

这些是 ROM 层面的事，App 改不了，只能引导用户设置：

- **国产 ROM 的后台清理**：MIUI / EMUI / ColorOS 等需要在系统设置里给 App
  开「自启动」「后台运行」「省电策略 → 无限制」，并锁进最近任务。
- **省电模式 / 超级省电**：会强制冻结所有后台进程，前台服务也不例外。
- **电池优化白名单**：`REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` 可以申请，
  但各大应用商店对它的使用有审核要求，本项目不主动申请，只在文档里说明。
